title: "POST /secure/sendbatch"
description: "Plusieurs messages en un appel. Les champs, le plafond d'expansion, et la réponse qui confirme bien moins qu'il n'y paraît."
---

Met plusieurs messages en file en un appel. **La réponse ne confirme que l'acceptation.** Les
résultats par-message arrivent sur votre URL d'errback.

```json
{
  "messages": [
    { "to": "61491570006", "content": "Your OTP is 4417." },
    { "to": "61491570007", "content": "Your OTP is 9921." }
  ]
}
```

```json
{
  "data": {
    "batchId": "c0ffee12-9f3a-4a1e-8d55-1b2c3d4e5f60",
    "messageCount": 3,
    "scheduled": "3600s"
  }
}
```

<Warning>
**`messageCount` est le nombre après expansion, pas le nombre qui a réussi.** Il n'y a pas d'id
par-message dans cette réponse et pas de résultat par-message. Voir
[Callbacks de batch](/developers/receive/batch-callbacks).
</Warning>

## Champs

| Champ | Type | Requis | Notes |
| :--- | :--- | :--- | :--- |
| `messages` | array | **oui** | Un objet par message, chacun prenant les champs d'un envoi unique. Son `to` peut aussi être un tableau. |
| `globals` | object | non | Valeurs par défaut **fusionnées sous** chaque message, donc un champ défini sur un message l'emporte. |
| `batch_config` | object | non | `schedule_at`, `callback_url`, `errback_url`. |

<Warning>
**Les autres clés dans `batch_config` sont ignorées, pas refusées.** Un `errback_url` mal
orthographié vous coûte chaque résultat par-message pendant que le batch renvoie encore `200`.

C'est le seul endroit de l'API où une faute de frappe ne produit pas un `400`. Vérifiez-le en
envoyant un batch contenant un message dont vous savez qu'il sera refusé.
</Warning>

## `schedule_at`

Exactement deux formes :

| Forme | Signification |
| :--- | :--- |
| `3600s` | Relative — dans une heure |
| `2026-08-20 09:30:00` | Absolue, `YYYY-MM-DD HH:MM:SS` |

Tout le reste est `412 Got unknown format`. **Une date dans le passé est refusée**, pas envoyée
immédiatement.

## Erreurs propres à cet endpoint

| Statut | `message` | Quand |
| :--- | :--- | :--- |
| 400 | `Mandatory argument messages is not found.` | Absent, non un tableau, ou vide. |
| 400 | `Argument messages has an invalid value: a batch may expand to at most 10000 messages.` | Les destinations en tableau se sont multipliées au-delà du plafond. |
| 412 | `Got unknown format: <value>, correct formats are …` | `schedule_at` dans aucune des deux formes acceptées, ou dans le passé. |

**Le plafond est 10 000 après expansion.** 100 messages ayant chacun 200 destinataires font
20 000, et sont refusés.

## Cadencement et durabilité

Les batches **se cadencent** contre la profondeur de la queue du router, en pausant au-dessus
d'un seuil haut. Vous n'avez pas à limiter vous-même la soumission d'un batch.

<Warning>
**Les batches planifiés ne survivent à un redémarrage qu'avec un broker RabbitMQ configuré**, et
pas même là quand la connexion au broker est dégradée. Si la planification durable compte,
confirmez avec votre fournisseur quel fournisseur de queue il exploite.
</Warning>

## Il n'y a pas d'endpoint d'état de batch

Ni dans FireFlo ni dans Jasmin. Le `batchId` corrèle les callbacks que vous recevez ; il n'y a
rien à sonder.
