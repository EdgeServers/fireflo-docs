---
title: "Sender IDs"
description: "Ce qui va dans `from`, pourquoi il peut nécessiter une approbation, et le défaut qui piège chaque nouvelle intégration."
---

`from` est ce que le destinataire voit comme expéditeur.

```json
{
  "to": "61491570006",
  "from": "SUNOTP",
  "content": "Your OTP is 4417, valid for 10 minutes."
}
```

## Le défaut est le piège

**Omettre `from` utilise votre nom de login.** C'est pratique en test et presque jamais correct en
production, parce que votre nom de login n'est habituellement pas un sender ID approuvé. Le même
code qui fonctionnait en staging renvoie donc `403` dès que l'approbation est imposée.

<Tip>
Fixez `from` explicitement dès le premier message, même quand l'approbation est désactivée. Cela ne
coûte rien et supprime toute une classe de surprises au go-live.
</Tip>

## Deux sortes de sender ID

| Sorte | Exemple | Le destinataire peut-il répondre ? |
| :--- | :--- | :--- |
| **Alphanumérique** | `SUNOTP` | Non |
| **Numérique** | `61491570006` | Oui |

L'alphanumérique est typiquement limité à 11 caractères, et le support varie selon les pays.
Certaines destinations le refusent entièrement, d'autres l'écrasent, et certaines exigent un
pré-enregistrement. Votre fournisseur sait ce qui s'applique à votre trafic.

## Quand l'approbation est imposée

Sur un compte avec le whitelisting de sender ID activé, un `from` non approuvé est refusé :

```json
{"message":"'SUNOTP' is not an approved sender ID for this account."}
```

`403` en HTTP, `0x415` en SMPP. Rien n'a été envoyé et rien n'a été débité.

**Ce n'est pas corrigeable dans le code.** Il faut une approbation de la part de celui qui exploite
votre passerelle, habituellement demandée via le portail client.

## En demander un

<Steps>
  <Step title="Demandez la chaîne exacte">
    `SUNOTP` et `SunOTP` sont des sender IDs différents. Demandez la casse que vous enverrez
    réellement.
  </Step>
  <Step title="Précisez pour quelles destinations">
    Les destinations réglementées — l'Inde en tête — exigent un enregistrement chez l'opérateur en
    plus de votre passerelle, et cela prend plus de temps.
  </Step>
  <Step title="Attendez APPROVED">
    Un sender ID en attente n'est pas utilisable. Il se comporte exactement comme s'il n'existait
    pas.
  </Step>
</Steps>

<Warning>
**Un sender ID approuvé peut aussi porter des TLVs**, qui sont apposés sur votre message quand il
correspond. Sur une voie DLT, ce stamp *est* l'identifiant d'entité enregistrée. Un expéditeur non
approuvé n'est donc pas seulement refusé pour être non approuvé ; il serait aussi arrivé chez
l'opérateur sans les paramètres dont il avait besoin.
</Warning>

## L'approbation du sender ID et l'approbation du contenu sont séparées

Deux vérifications différentes, deux refus différents :

| Vérification | Refus |
| :--- | :--- |
| Ce `from` est-il approuvé ? | `not an approved sender ID` |
| Ce libellé correspond-il à un template approuvé ? | `does not match any approved template` |

Un compte peut imposer l'une, les deux ou aucune. Passer l'une ne dit rien de l'autre. Voir
[Refus](/platform/troubleshooting/refusals) pour lire la seconde.
