---
title: "Inspecter une file"
description: "La profondeur vous dit que quelque chose est bloqué ; un dump vous dit quoi. Le seul champ qui sépare un problème de volume d'un problème vendeur. Et comment nettoyer une file honnêtement quand ses messages ne partiront jamais."
---

`/ops/health` dit à quelle profondeur est chaque file. Cela suffit à savoir que quelque chose est bloqué et **ne suffit pas à faire quoi que ce soit à ce sujet** : 4 000 messages en attente sur `vendor1` se lit identiquement que ce soit le batch loupé d'un client ou chaque compte sur la boîte.

```bash
./scripts/fireflo queue dump
./scripts/fireflo queue dump vendor1
./scripts/fireflo queue dump vendor1 100
```

Un nombre nu est lu comme une **limite** plutôt qu'un nom de worker, donc `queue dump 100` élargit tout. Le défaut est 20 par file, plafond 500. Au-delà la question appartient à `cdr_submit` plutôt qu'à un gateway en direct.

```json
{
  "data": {
    "observed_at": "2026-08-09T02:14:07Z",
    "limit_per_queue": 20,
    "queues": [
      {
        "name": "router", "kind": "router", "depth": 1204, "ordered": true, "returned": 20,
        "entries": [
          {
            "serial": "01JC8…", "account": "acct-in-2001", "product": "in-otp",
            "from": "SUNOTP", "to": "919876543210",
            "body_chars": 44, "encoding": "gsm7", "parts": 1,
            "retries": 0, "priority": 2, "ingress": "http", "target": "in-sim",
            "queued_at": "2026-08-09T02:14:05Z"
          }
        ]
      }
    ]
  }
}
```

## Les quatre types

| `kind` | Contient |
| :--- | :--- |
| `router` | Accepté, pas encore routé. **Une file pour tout le gateway.** |
| `pending` | Routé vers un vendeur, en attente de sa session. Une par worker. |
| `delayed` | Retries planifiés. `ready_in_ms` dit combien de temps avant que chacun soit éligible. |
| `broker` | Retenu sur RabbitMQ. **Profondeur seulement.** Voir ci-dessous. |

## `retries` est le champ qui répond à la question

<Tip>
**Une file pleine de zéros est un problème de volume.** Plus est arrivé que le vendeur peut prendre.

**Une file pleine de retries non nuls est un problème vendeur.** Les mêmes messages reviennent.

Ceux-là demandent des réponses opposées. Ajouter de la capacité à une tempête de retries la rend pire ; suspendre un vendeur qui est juste occupé déplace le backlog quelque part de plus coûteux.
</Tip>

**`depth` et `returned` sont des questions différentes.** `depth` est toute la file ; `returned` est combien a été listé. Les comparer est comment vous dites si vous voyez le problème ou un coin.

## Pas de texte de message, et pas de drapeau qui en ajoute un

`cdr_submit` exclut le corps par principe. Destination et source sont gardées parce que la tarification et les litiges en ont besoin, le texte non parce qu'exploiter un gateway ne le fait jamais.

Un dump de file hérite de cette règle plutôt que de devenir la seule surface opérateur qui redonne du trafic client en gros.

`body_chars` avec `encoding` distingue un OTP en une partie d'un blast bloqué à six parties, ce qui est la question de diagnostic réellement posée.

## Rien n'est consommé et rien n'est réordonné

Chaque file est parcourue avec son propre itérateur **pendant que le gateway continue de la drainer**. Donc :

- Un message listé peut déjà être parti au moment où vous le lisez.
- `depth` est échantillonnée après le parcours et peut différer de `entries` de quelques-uns.
- `ordered` dit si la liste est l'ordre dans lequel le gateway enverra. **False** pour une file de priorité et pour la file de délai.

C'est le compromis honnête. L'alternative est d'arrêter le trafic pour le regarder.

## Une file broker est rapportée mais jamais parcourue

AMQP n'a pas de moyen de regarder un message en file sans le prendre. `basicGet` plus un requeue réordonnerait la file et réinitialiserait les comptes de livraison sur les messages des clients payants pour satisfaire un diagnostic.

Donc la profondeur est rapportée et le dump le dit. **Un broker qui ne répond pas rapporte la profondeur comme inconnue plutôt que comme zéro.** Ce qui compte, parce que zéro est une affirmation et inconnu ne l'est pas.

## Nettoyer une file : archiver, puis terminer

<Warning>
**Stop sending ou Hold d'abord.** Si vous avez besoin que le trafic s'arrête, suspendez le vendor ou
retenez le listener ([Contrôle des workers](/platform/operations/worker-control)) : rien n'est perdu,
et la reprise continue là où elle s'était arrêtée. Ne nettoyez une file que pour des messages qui ne
partiront jamais : un vendor qui n'existe plus, une réserve de routage que personne ne corrigera, des
accusés pour un login qui ne se bindera plus jamais.
</Warning>

À partir de 0.12.19, une file peut être nettoyée, en ligne de commande ou depuis le panneau de
contrôle ; les deux appellent le même endpoint du gateway, avec le token admin :

```bash
./scripts/fireflo queue archive worker --worker smppclient.vendor1 --sub held   # dry run: counts, refund total, sample
FIREFLO_QUEUE_ARCHIVE=true ./scripts/fireflo queue archive worker --worker smppclient.vendor1 --sub held \
      --note "vendor withdrawn" --yes
```

Ce qui arrive à chaque message correspondant, dans cet ordre :

1. **Retiré de la file** — de façon atomique : un message est pris par la session du vendor ou par le
   nettoyage, jamais les deux. Le gateway continue de tourner ; rien n'a besoin d'être suspendu
   d'abord.
2. **Archivé**, dans une seule transaction de base de données validée, avec qui l'a fait, pourquoi
   (la note) et le lot auquel il appartient. Si l'archive ne peut pas être écrite, chaque message est
   remis en file et la commande répond qu'elle n'a pas pu — rien n'est perdu.
3. **Terminé**, exactement comme un message que le gateway abandonne lui-même : **remboursé** s'il a
   été facturé, un **accusé d'échec** envoyé là où le client en a demandé un, et enregistré comme
   `REJECTED` avec le motif `operatorPurge` — ce que montrent la chronologie du message et la page
   Refused.

Les accusés qui attendent un login et les retries de callback webhook ne portent pas d'argent : ils
sont archivés et supprimés. **Rien d'archivé ne peut être remis** — nettoyer termine un message, cela
ne le met pas de côté.

| Store | Contient | Sous-stores |
| :--- | :--- | :--- |
| `worker` | Les files d'un vendor ou d'un listener | `pending`, `retry`, `held` (pendant l'arrêt), `parked` (l'entrant d'un listener pendant l'arrêt) |
| `routing` | Les files à l'échelle du gateway avant qu'un vendor soit choisi | `router`, `retry`, `failed` (réserve des échecs de routage) |
| `receipts` | Les accusés qui attendent qu'un login SMPP se binde | par login ou compte |
| `callbacks` | Les callbacks webhook qui attendent d'être réessayés | par compte |

Un nettoyage d'un store worker ou routing sans vendor, listener, compte ni login nommé est refusé à
moins que vous ne disiez `--all`. Chaque appel archive au plus 10 000 messages ; la commande et le
panneau travaillent par lots jusqu'à ce que plus rien ne corresponde.

<Note>
**Une file tenue sur le broker de messages ne peut pas être nettoyée.** AMQP ne peut pas lire un
message sans le prendre, et un nettoyage doit voir un message pour l'archiver — donc une file sur le
broker est refusée avec `broker-backed`, et l'outillage propre au broker est le moyen de s'en occuper.
</Note>

L'archive se lit dans **Reports → Archives → Queue housekeeping** dans le panneau, ou avec
`fireflo queue archived` et `fireflo queue archive summary` ; elle est conservée en partitions
mensuelles à côté d'un résumé par jour qui n'est jamais supprimé. Voir
[la référence des commandes](/reference/cli/fireflo#queues).

## Accès

Le token **de lecture**, pas l'admin. Un dump ne prend rien et ne bouge rien, donc un système de monitoring tenant le secret de surveillance peut le demander.
