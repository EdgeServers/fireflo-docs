`/secure/sendbatch` queues many messages in one call.

```json
{
  "messages": [
    { "to": "61491570006", "content": "Your OTP is 4417." },
    { "to": "61491570007", "content": "Your OTP is 9921." }
  ]
}
```

Each element takes the same fields as a single send. A message's `to` may itself be an array, which
multiplies out.

## The response confirms acceptance only

```json
{
  "data": {
    "batchId": "c0ffee12-9f3a-4a1e-8d55-1b2c3d4e5f60",
    "messageCount": 3,
    "scheduled": "3600s"
  }
}
```

<Warning>
**There are no per-message ids in this response, and no per-message results.** `messageCount` is how
many the batch expanded to, not how many succeeded.

Per-message outcomes arrive on your **errback URL** as separate callbacks. A client that treats a
`200` here as "all three sent" is wrong in exactly the cases worth knowing about.
</Warning>

## Defaults and configuration

```json
{
  "messages": [
    { "to": "61491570006", "content": "Your OTP is 4417." },
    { "to": "61491570007", "content": "Your OTP is 9921." }
  ],
  "globals": {
    "from": "SUNOTP",
    "dlr": "yes",
    "dlr_url": "https://yourapp.example.com/hooks/dlr"
  },
  "batch_config": {
    "schedule_at": "3600s",
    "callback_url": "https://yourapp.example.com/hooks/batch-done",
    "errback_url": "https://yourapp.example.com/hooks/batch-error"
  }
}
```

**`globals` is merged *under* every message**, so a field set on an individual message wins.

<Warning>
**Unknown keys in `batch_config` are ignored, not refused.** A typo in `errback_url` costs you every
per-message result, silently — the batch is accepted and the callbacks simply never arrive.

This is the one place on the API where a misspelled field does not produce a `400`, so check it by
sending a deliberately failing message and confirming the callback lands.
</Warning>

## Scheduling

`schedule_at` takes exactly two forms:

| Form | Meaning |
| :--- | :--- |
| `3600s` | Relative — in one hour |
| `2026-08-20 09:30:00` | Absolute, `YYYY-MM-DD HH:MM:SS` |

Anything else is `412 Got unknown format`. **A date in the past is refused too**, rather than sent
immediately.

<Tip>
Scheduled batches survive a restart only when the gateway is running with a RabbitMQ broker — and not
even then while the broker connection is degraded. If durable scheduling matters to you, ask your
provider which queue provider they run and whether they alert on `amqp.bridge.degraded`.
</Tip>

## Limits

| Limit | Value |
| :--- | :--- |
| Messages per batch after expansion | **10 000** |
| Above that | `400 a batch may expand to at most 10000 messages` |

Array-valued destinations multiply: 100 messages each with 200 recipients is 20 000, and refused.

## Pacing

Batches pace themselves against the router queue's depth, pausing above a high-water mark. You do not
need to throttle your own submission of a batch — but you **do** still need to respect your account's
messages-per-second limit on ordinary sends, which is a separate ceiling and returns `429`.
