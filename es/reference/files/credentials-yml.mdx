Perfiles de autenticación para clientes que se conectan a FireFlo. Binds SMPP y llamantes REST por igual.

Recargado en caliente: un hilo virtual en segundo plano vigila el archivo y aplica un cambio en unos 200 ms,
con un debounce, y sin reinicio.

## Campos

| Campo | Tipo | Descripción |
| :--- | :--- | :--- |
| `type` | String | `SMPP` o `HTTP`. |
| `systemId` | String | El nombre de usuario o identificador de sistema. |
| `password` | String | La contraseña para ese `systemId`. |
| `apiKey` | String | Clave opcional de búsqueda HTTP. |
| `allowedIps` | Lista | Direcciones IP explícitas autorizadas a usar esta credencial. |
| `allowedProducts` | Lista | Productos que este login puede nombrar en un envío REST, más allá del suyo. |
| `accountId` | String | Enlaza la credencial a una cuenta. **La clave de facturación**. |
| `product` | String | Asocia la credencial con un producto. |
| `defaultTlvs` | Map | Valores TLV suministrados por cuenta del cliente cuando un `submit_sm` entrante no los lleva. |

```yaml
- type: SMPP
  systemId: "acme-smpp"
  password: "REPLACE_WITH_A_UNIQUE_STRONG_SECRET"
  accountId: "acct-1001"
  product: "premium"
  defaultTlvs:
    peid_0x1400: "1101234567890123456"
    acct_0x1403: "MESSAGE:owner_id"
```

## Validación, por protocolo

| Tipo | Debe proporcionar | Clave de búsqueda |
| :--- | :--- | :--- |
| `SMPP` | `systemId` **y** `password` | `systemId` |
| `HTTP` | `apiKey`, **o** ambos `systemId` y `password` | `apiKey` si está presente, si no `systemId` |

<Warning>
**Para la API REST, configura tanto `systemId` como `password`** y envíalos como HTTP Basic. La
clave de búsqueda es el usuario Basic.

Una credencial que solo tiene un `apiKey` y sin password es configuración válida y **no puede
autenticar**. Se rechaza con `403`.
</Warning>

## `allowedIps` y `allowedProducts` predeterminan en direcciones opuestas

Eso es deliberado, y vale la pena leerlo dos veces.

| Campo | Vacío o ausente significa |
| :--- | :--- |
| `allowedIps` | **Sin restricción**. Conéctate desde donde sea |
| `allowedProducts` | **Rechaza el campo `product` totalmente** |

El producto selecciona la tarifa. Un login que pudiera nombrar cualquier producto podría elegir su propio precio, así que
nombrar uno que no le ha sido concedido se rechaza en lugar de permitirse por omisión.

## `product`, y de dónde viene

Para un bind SMPP, el `system_type` en la petición de bind **tiene precedencia** cuando el cliente envía
uno; este campo es el fallback. Los llamantes HTTP siempre usan este valor, porque no hay bind.

Un producto sin establecer es un estado soportado. Coincide con `product:isNull:` en la tabla de enrutamiento y se tarifica
solo por reglas de tarifa que a su vez no llevan producto.

<Warning>
Ese predeterminado tiene un coste. `RateSnapshot.rulesFor` muestra a un mensaje sin producto **solo** las reglas
sin producto. Así que en un despliegue cuyas reglas de tarifa todas llevan uno, un mensaje sin producto no coincide
con nada, se queda sin tarificar, y un mensaje sin tarificar nunca se cobra. Se entrega y se factura a
nadie.

[`conf.product.required` y `smsg.restapi.product.required`](/reference/config/limits) lo cierran, y
ambos están apagados por defecto.
</Warning>

## TLVs por defecto

Aplicados en el ingreso, **tras** los tags llevados en el propio `submit_sm`. Un valor que el cliente envió
siempre gana. Se ejecutan **antes** de la comprobación `mandatory.tlvs.submit` de la pasarela, así que una credencial puede
satisfacer un tag requerido en nombre de un cliente que nunca envía uno.

Las claves usan la gramática `<name>_<tag>` en [Declaraciones TLV](/reference/smpp/tlvs). Los valores pueden ser un
literal, `MESSAGE:<field>` para copiar un atributo del mensaje, o `hex:<bytes>`.

<Note>
**Los defaults TLV de credenciales se snapshotean cuando un cliente hace bind**. A diferencia de los archivos de enrutamiento y propiedades.
Editarlos aplica en el **siguiente bind** de ese cliente, no a sesiones ya conectadas.
</Note>

## Las claves desconocidas se avisan, no se rechazan

Así que una configuración más nueva permanece cargable en un build más antiguo. Cada clave desconocida se registra como advertencia.

<Warning>
Un **error tipográfico se descarta silenciosamente** en lugar de rechazarse. Si un campo parece no tener efecto, lee el log
tras editar.
</Warning>

En modo base de datos este archivo no se lee tras el arranque; los mismos datos viven en `app_credential`. Consulta
[Base de datos](/reference/config/database).
