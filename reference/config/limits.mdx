## Queue limits

| Property | Scope | Default | Description |
| :--- | :--- | :--- | :--- |
| `smsg.queue.capacity` | global | `0` (unbounded) | The most messages the router queue, and each outbound worker queue, will hold. |
| `inQueue.capacity` | per listener | `0` (unbounded) | The most messages one SMPP listener will hold waiting to be written to the message store. |

**Why they exist.** The gateway answers a submission *before* it routes it, so every message in these
queues has already been accepted and charged for. Unbounded, a vendor that stops accepting plus a
listener that keeps accepting grows the heap until the JVM is killed — and every queued message dies
with it, none refunded, none recorded as anything but PENDING.

**What a limit changes.** Only the two ingresses refuse. Inside the gateway a full queue is still
backpressure, and the router waiting on a full worker queue is the router going at the speed the
vendor can take. At an ingress there is a client holding a connection open, so waiting would stall
that session rather than slow it down:

| Ingress | When the queue is full |
| :--- | :--- |
| SMPP | `submit_sm_resp` with `ESME_RMSGQFUL` (`0x14`). Nothing is charged — the refusal happens before the message is accepted. |
| REST | `503` with `queueFull` in `cdr_rejected`. Anything already charged is refunded, because the REST path charges before it publishes. |

A message refused because its **credit** was not confirmed is not a full queue, and from 0.17.2 it is
not recorded or answered as one — see the next section. Before 0.17.2 it answered `0x14` over SMPP and
was recorded `queueFull` over REST and gRPC.

<Note>
**Choosing a number.** There is no default because a limit is a statement about your own traffic and
your own heap. Too low refuses messages that would have been delivered; too high and it never fires
before the JVM does.

Start from how many messages you are willing to hold for a vendor that has gone quiet, and check the
depth under normal load first — `router_queue` and each worker's `queue_depth` are on
[`/ops/health`](/reference/management/endpoints), with the limit beside them once one is set.
</Note>

## Waiting for credit

On a prepaid gateway a message that finds no credit in hand waits for the account's next credit block
rather than being refused. These bound that wait. From 0.17.2.

| Property | Scope | Default | Description |
| :--- | :--- | :--- | :--- |
| `smsg.balance.park.seconds` | global | `10` | How long a message waits for its credit before it is refused `creditPending`, uncharged. 1 to 30, read on every use. Over SMPP the whole wait; over the HTTP API, gRPC and the platform API at most 5 seconds of it. |
| `conf.status.creditPending` | per listener | `0x00000058` | The `submit_sm_resp` status for that refusal. Hex or decimal; a value that is not a number falls back to the default with a warning. Default `ESME_RTHROTTLED`, which clients resend; set `0x14` to keep the answer before 0.17.2. |

**What it limits.** The time between a submit arriving and the gateway answering it, while its credit
is being reserved. Nothing is charged or sent before the credit is reserved, so the wait holds the
answer, not the money. A reservation that fails because the database is slow or not answering is
retried during the wait.

<Warning>
**Keep `smsg.balance.park.seconds` below your customers' SMPP response timeout.** A client that stops
waiting before the gateway answers resends the submit, and if the first is then accepted, both are
sent. The default of 10 seconds is below the usual client defaults.
</Warning>

Two fixed caps stop the wait becoming a heap problem of its own: when **10,000** of one account's
messages, or **100,000** across the gateway, are already waiting, the next is refused at once as
`creditQueueFull` — `0x14` over SMPP, a full-queue `503` over the API — uncharged.

The answers, the causes and what to look at are in
[Refusals](/platform/troubleshooting/refusals#credit-not-confirmed-in-time).

## HTTP ingress limits

| Property | Default | Description |
| :--- | :--- | :--- |
| `smsg.restapi.maxRate.default` | `0` | Messages per second per billing account, **REST and gRPC together** (from 0.15.9). `0` is unlimited. |
| `smsg.restapi.maxRate.<accountId>` | *(unset)* | Ceiling for one account, overriding the default. |
| `smsg.restapi.coding.autodetect` | `true` | From 0.16.2. A send over the HTTP API, gRPC or the platform API that names no `coding` goes as UCS-2 (coding 8) when its text has a character GSM-7 cannot carry, and is counted at 70 / 67 characters a segment. Platform-wide, read on every send. A `coding` named on the send, or in a batch's `globals`, always wins. `false` restores the behaviour before 0.16.2: default alphabet, `?` for what it cannot carry. SMPP is not affected. |
| `quarkus.http.limits.max-body-size` | `1M` | Largest request body accepted. |
| `quarkus.http.read-timeout` | `60S` | How long a request may take to arrive. |
| `quarkus.http.idle-timeout` | `30M` | How long an idle connection is held. |

Keyed on the **account**, not the credential: one account may hold several logins, and a per-login key
would let a customer raise their own ceiling by creating another one.

The [gRPC API](/platform/operations/grpc) has no ceiling of its own, deliberately: its sends count
against this one, so moving traffic from REST to gRPC cannot double what an account is allowed.

The check runs before the message is rated or charged, so a refused message is never billed. The
caller gets `429`, deliberately not `403` — nothing about the request or the credential is wrong.

<Warning>
Counted **per process**. A multi-instance deployment allows this rate on each instance, so the
effective ceiling is the rate times the instance count. It is a guard against a runaway sender, not a
distributed quota.

The SMPP listener has its own ceiling (`conf.maxRate.default`) and the two do not track each other.
Set both when the limit is meant to be gateway-wide.
</Warning>

## Batch limits

| Property | Default | Description |
| :--- | :--- | :--- |
| `smsg.restapi.batch.max.messages` | `10000` | Largest a batch may expand to, counting **destinations** rather than entries. |
| `smsg.restapi.batch.concurrency` | `4` | How many batches run at once. Sized at startup, so a change needs a restart. |
| `smsg.restapi.batch.rate.per.second` | `0` | Ceiling on how fast one batch is fed into the router. `0` is unpaced. |
| `smsg.restapi.batch.queue.highwater` | `100000` | Router-queue depth at which batch expansion pauses and waits for it to drain. |

Same reasoning as the queue limits: the router queue is unbounded by default and cannot push back, so
an uncapped batch is a way to exhaust the heap.

## Reseller account writes

From 0.17.3. These bound what a reseller does through the reseller API (`/secure/accounts`): creating
and changing its customers' accounts and logins. **They limit account management, not message
traffic** — no send, receipt or read is counted.

| Property | Scope | Default | What it limits |
| :--- | :--- | :--- | :--- |
| `smsg.reseller.max.children` | per reseller | `500` | Live accounts one reseller may hold. Archived accounts are not counted. Over it, creating an account answers `409`, code `LIMIT_REACHED`. |
| `smsg.reseller.max.logins.per.account` | per account (each of a reseller's accounts) | `50` | Logins one such account may have, disabled ones included. Over it, adding a login answers `409`, code `LIMIT_REACHED`. |
| `smsg.reseller.writes.per.minute` | per reseller, per gateway node | `120` | Account-management writes in one minute: creating or changing an account or a login, setting a password, recharging, withdrawing. Over it the write answers `429`, code `RATE_LIMITED`, with `Retry-After` set to the seconds left in the minute, and nothing is done. Reads are not counted. |

All three are gateway-wide settings read on each use, so a change needs no restart; `0` or less means
the default. The refusal names the key. A reseller already above a cap keeps what it has and cannot
add more until the key is raised. The minute is counted on each node, so in a cluster a reseller can
make this many writes on every node.

## Product and rating refusals

Three switches, **all off by default**, that turn a quiet misconfiguration into a loud one.

| Property | Scope | Default | Description |
| :--- | :--- | :--- | :--- |
| `conf.product.required` | per listener | `false` | Refuse a bind whose resolved product is blank or names no enabled `app_product` row. |
| `smsg.restapi.product.required` | global | `false` | The REST twin, checked at submit since there is no bind. |
| `smsg.rating.unrated.refuse` | global | `false` | Refuse a message that matched no sell-side rate rule, instead of accepting it and charging nothing. |

<Warning>
Read this before turning any of them on: **each converts traffic that flows today into traffic that is
refused.**
</Warning>

**Why they exist.** An unset product is a supported state that sends messages for free.
Rating looks up a message with no product in the any-product rules alone, so a
product-less message can never reach a product-scoped rule. Nothing matches, the message is left
unrated, and the credit charge returns early. On an account whose rate rules all carry a product, that
is the whole bill.

**`system_type` is the hole a non-empty check would not have closed.** On an SMPP bind it resolves
*over* the credential's product and is free text validated nowhere, so a customer binding `prem`
instead of `premium` passes any non-empty test and lands in exactly the same unrated state. That is
why the check is membership of the catalogue rather than presence of a value.

<Note>
**File mode has no catalogue.** `credentials.yml` has nothing to derive one from, so the membership
half is skipped and only the non-empty half applies, logged once per configuration load naming the
listener. This is the one place the feature is weaker than it sounds.
</Note>

`conf.product.required` is checked at **bind**, after authentication, because the product lives on the
session context. `smsg.restapi.product.required` also applies to `/secure/rate`, so a quote cannot
price traffic a send would refuse.

Before switching either product flag on, the control panel's pre-flight report lists every enabled
credential that would stop binding. Its honest limit is stated on that page: for SMPP it checks the
credential's fallback, and a mistyped `system_type` is invisible to it.

Refusal codes are `0x40F` and `0x418` — see [Status codes](/reference/smpp/status-codes).
