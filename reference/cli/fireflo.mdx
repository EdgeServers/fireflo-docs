`scripts/fireflo` is the operator's command line. It talks to three different things depending on the
verb, and knowing which is most of knowing how to use it.

| Group | Talks to | Needs a running gateway |
| :--- | :--- | :--- |
| `db`, `bootstrap`, `import`, `show` | The database directly | No |
| `send`, `selftest` | The **message** port, as a customer would (`selftest` reads the database too) | Yes |
| everything else | The **operational** port, 9000 by default | Yes |

<Warning>
`show` reads the database, which is **not the same as what the gateway is doing**. In file mode it is
not reading those tables at all; in database mode it holds a cached snapshot and re-reads on a poll.

For what is actually in force — including whether whitelisting ever loaded — use `health`.
</Warning>

## Database and offline

```bash
fireflo db test        # reachable, authenticated, migrated, permitted, answered — separately
fireflo db info        # applied and pending versions
fireflo db validate    # do the applied migrations still match the files
fireflo db migrate     # apply what is pending      (needs FIREFLO_DB_MIGRATE=true)
fireflo db repair      # realign Flyway history with the files
fireflo db secrets status | seal | open   # customer passwords at rest (needs FIREFLO_SECRETS_KEY to seal or open)
```

`info` and `validate` do **not** need the write-enabling flag. Reading the schema version changes
nothing, and needing a flag before you may look would be a trap in the middle of an incident.

`db secrets` is how encryption at rest is turned on for an install that already has customers:
with `FIREFLO_SECRETS_KEY` set on the gateway and the control panel, `seal` rewrites every stored
password in one transaction, `status` counts what is sealed and what is not, and `open` is the way
back before removing the key. From then on every password either side writes is sealed as it is
written. See [tokens and access](/platform/operations/tokens-and-access#customer-passwords-at-rest).

### bootstrap

```bash
fireflo bootstrap [--port N]
```

Writes the least a fresh database needs to start: a `default` routing table, an empty `MESSAGE` table
for a vendor to go in, one listener on 27777, and one SMPP login whose password it generates and
prints **once**.

It writes nothing else on purpose — no vendor, because one needs a host and credentials nobody can
guess; no rates, because an invented price bills silently where an absent one shows up unpriced. Both
absences are named in its closing output.

Optional flags fill those in when you do know them — the installer passes them when you choose
SMPPSim:

| Flag | Writes |
| :--- | :--- |
| `--vendor NAME --vendor-host H --vendor-port P --vendor-system-id ID --vendor-password-file F` | An SMPP vendor, and a catch-all to it in `MESSAGE`. All five or none; the password is read from the file, never the command line |
| `--vendor-cost RATE` | A cost on that vendor, so margins are real |
| `--product P --rate R --currency C` | The first price, on the login's product |
| `--opening-balance AMOUNT` | Prepaid credit on the first account, recorded as a recharge |
| `--login-file F` | An HTTP login `fireflo-http` on the same account, its password saved to `F` (owner-only) for `selftest` |

<Note>
`bootstrap` refuses the moment it finds a routing table, a worker or a login, so it cannot overwrite a
running deployment. There is no flag that makes it.
</Note>

### import

```bash
fireflo import all --dry-run                          # parse, report, write nothing
FIREFLO_CONFIG_IMPORT=true fireflo import all --replace
```

Subjects are `all` (default), `rates`, `routing`, `credentials`. Flags: `--dry-run`, `--replace`,
`--replace-filters`, `--prune`, `--rates-file`, `--routing-file`, `--currency`.

**Run the dry run and read it.** It classifies every rate scope as a vendor cost or an account price
and names the ones it can classify as neither — which is how a scope that will load and silently match
nothing gets caught before it does.

<Warning>
**Credentials have one refusal the others do not.** An import yielding no usable credential is refused
unconditionally, flag or no flag. An empty `app_credential` plus `FIREFLO_CONFIG_SOURCE=db` refuses
every bind and every REST call at once, and nothing in the logs names the cause.
</Warning>

Exit codes: `0` fine, `1` the migration failed, `2` refused without touching anything — so a deploy
pipeline can tell a missing flag from a broken migration.

### show

```bash
fireflo show config [pattern]     workers     worker <name>
fireflo show routing              rates [scope]
fireflo show account [id]         whitelist [id]      rejected [id]
```

`whitelist` prints the four gates in the order they apply, then what is approved. `rejected` is what
was refused in the last 24 hours, and why.

## Sending one message

```bash
fireflo send <from> <to> <text>
```

Goes through the HTTP API exactly as a customer would. Needs `FIREFLO_SEND_LOGIN` and
`FIREFLO_SEND_PASSWORD`.

### smppsim-setup

```bash
fireflo smppsim-setup --vendor-port P --vendor-system-id ID --vendor-password-file F \
    [--vendor NAME] [--vendor-host H] [--vendor-cost RATE] [--account ID --login-file F] [--no-route]
```

Adds an SMPP vendor — SMPPSim by default — to a configuration that already exists. It writes:

- the vendor, or refreshes its connection details when it's already there;
- its cost, only when it has no cost rules yet;
- a catch-all to it in `MESSAGE`, only when `MESSAGE` has none;
- an HTTP login `fireflo-selftest` on the account, saved owner-only for `selftest`.

One transaction, so a refusal writes nothing. Safe to run again. `fireflo-install smppsim` runs it.

### selftest

```bash
fireflo selftest [--to N] [--from S] [--account ID] [--expect-vendor NAME] [--login-file F] [--timeout 60]
```

Sends **one real message** and follows it through every record it leaves, printing PASS, FAIL or
SKIP for each step and why:

| Step | Checks |
| :--- | :--- |
| send | The gateway accepted it. A `402` is a FAIL: no prepaid credit |
| routed | A call record names the vendor it went to (and it is `--expect-vendor`, when given) and the rule that sent it |
| billed | It carries a price and the rule that set it, plus cost and margin when the vendor has a cost. SKIP when no price rule matched |
| delivered | A final outcome came back from the vendor |
| debited | With prepaid on, the account's balance fell by exactly the price |

The debit is read from the balance the account's owner sees — the durable balance plus the
gateway's unspent reservation — before and after the send, so it needs no admin token and works on
an unlicensed gateway. It signs in with `FIREFLO_SEND_LOGIN` and `FIREFLO_SEND_PASSWORD`, or the
login bootstrap saved. It changes no configuration.

Exit codes: `0` nothing failed, `1` a step failed, `2` misused. The installer runs it at the end of
an install with SMPPSim; run it again whenever you want to know the path still works end to end.

## Operational

```bash
fireflo health          # live state
fireflo version         # which release is RUNNING, asked of the gateway
fireflo verify          # is this deployment actually working
fireflo reload          # re-read configuration without a restart
```

`version` asks the gateway rather than the files on disk — an artefact that was built but never
restarted into is the whole reason to ask.

`verify` checks in the order that makes the first failure the informative one: the artefact is
complete, Java is new enough, the message port answers, the operational port agrees with the
configuration you chose, and the two tokens are genuinely separate. It ends by saying whether it can
send yet, which is not the same question as whether it is running.

<Note>
**`verify` exit code 4** means the deployment is sound but this install's own data is not — for
example nothing is configured to route to. `0` is fine, `1` failed, `2` refused or misused.
</Note>

### Credit

```bash
fireflo credit release [account]
```

Returns unspent RESERVED prepaid credit so the next message re-reads the balance.

<Warning>
**This is the one piece of runtime state `reload` cannot rebuild.** Credit is handed out in blocks and
stays spendable until used, so correcting a balance by hand does not take effect until this runs. It
takes nothing away — the block is reservable again immediately.
</Warning>

### Queues

Every queue action the control panel offers has a command, and both call the same gateway endpoint,
so the outcome is identical whichever you use.

**See what is waiting** — read token, changes nothing:

```bash
fireflo queue dump smppclient.acme 50          # a vendor's pending, retry and held entries
fireflo queue dump smppserver.smpp             # a listener's parked inbound
fireflo queue dump routing                     # router queue, routing retry, failed-routing park
fireflo queue dump receipts --system-id acme01 # unpushed receipts for an SMPP login
fireflo queue dump callbacks --account acme    # webhook retries waiting on a dead endpoint
```

Lists the messages waiting, not just how many — account, product, destination, retry count and age.
Nothing is taken off a queue and nothing is reordered. Default 20 per queue, maximum 500. There is no
message text in the output, by the same rule that keeps it out of call records by default.

**Clean a queue: archive, then end** — admin token; a dry run unless you pass `--yes` **and** set
`FIREFLO_QUEUE_ARCHIVE=true`:

```bash
fireflo queue archive worker --worker smppclient.acme --sub held                 # dry run: counts, refund total, sample
FIREFLO_QUEUE_ARCHIVE=true fireflo queue archive worker --worker smppclient.acme --sub held \
      --note "stuck after vendor outage" --yes                                    # archive and end them
fireflo queue archive worker --account acme --older-than 2h --sub pending        # one account across all vendors
fireflo queue archive routing --sub failed --older-than 1d --all                 # failed-routing park, every account
fireflo queue archive receipts --system-id acme01 --older-than 3d                # receipts for a login that never binds
fireflo queue archive callbacks --account acme                                   # webhook retries for one account
fireflo queue archive spill --include-today                                      # import spill files into call records, then remove
```

| Option | Meaning |
| :--- | :--- |
| `--worker W` | A vendor (`smppclient.<name>`) or a listener (`smppserver.<name>`) |
| `--account A` / `--system-id S` | One account, or one SMPP login |
| `--older-than 2h` | Only entries queued longer ago than this (`s`, `m`, `h`, `d`) |
| `--sub` | `pending`, `retry`, `held`, `parked` (worker); `router`, `retry`, `failed` (routing) |
| `--limit N` | At most N per batch, up to 10,000 |
| `--all` | Required to clean a worker or routing store with no vendor, listener, account or login named |
| `--note TEXT` | Why. Recorded on every archived entry |

Each matched message is **archived first** — one committed database transaction — and then ended
exactly as a message the gateway drops itself: refunded if it was charged, a failed receipt sent where
the customer asked for one, and recorded as `REJECTED` with reason `operatorPurge`, which is what its
timeline shows. Receipts and callback retries carry no money; they are archived and removed. With
`--yes` the command works in batches until nothing more matches, printing running totals. **Nothing
archived can be put back.**

For spill files, "archive" means the records they hold are imported into the call-record tables, the
import is recorded, and only then is the file deleted. Today's file is skipped unless you pass
`--include-today`, because the gateway may still be writing to it.

<Warning>
Stop sending or Hold is still the first tool. Use them when you need traffic to stop; clean a queue
only for messages that will never be sent. A queue held on the message broker (RabbitMQ) cannot be
cleaned this way — AMQP cannot read a message without taking it — and the command says so.
</Warning>

**Read the archive** — database credentials from your env file, no running gateway needed:

```bash
fireflo queue archived --account acme --since 7d             # archived entries, newest first
fireflo queue archived --batch 6f1c…                         # one run's entries
fireflo queue archive summary                                # per month: rows, first/last time, size, purged months
fireflo queue archive summary --by account --since 2026-01   # reconciliation: messages, refunded, receipts, price per account
fireflo queue archive summary --by day --account acme
```

The archive is kept in monthly partitions, like the call records, beside a per-day summary — per
account, store, kind and worker: messages archived, refunded, receipts sent and price total — that is
**never deleted**. `--by account` reads that summary, so it reconciles the same before and after old
months are purged.

**Delete old archive months** — a dry run unless you pass `--yes` **and** set
`FIREFLO_QUEUE_ARCHIVE_PURGE=true`:

```bash
fireflo queue archive purge --before 2026-04                 # dry run: months, rows, reconciled totals
FIREFLO_QUEUE_ARCHIVE_PURGE=true fireflo queue archive purge --older-than 180d --yes
```

Only whole months entirely before the cutoff go, never the current month. Each month is reconciled
first: its row count, overall and per account, must equal the summary's for those days. A month that
does not reconcile is refused with both numbers and nothing is deleted (exit `2`). The summary rows of
a purged month are kept and marked purged, with the row count. A cutoff in the middle of a month keeps
that month and says so.

The archive is never deleted automatically unless `smsg.queue.archive.retention.days` is set (default
`0`, never); then the gateway's expiry sweep runs this same reconciled purge.

<Note>
The admin token is shared, so the gateway records the actor the command sends — `$USER@host` — on
every batch. From the control panel it is the signed-in user's address.
</Note>

### Receipts

**Re-send delivery receipts to an SMPP login for a period** — admin token; a dry run unless `--yes`:

```bash
fireflo receipts repush --system-id acme01 --from 2026-10-01 --to 2026-10-07              # dry run: messages, receipts by state, bound now?
fireflo receipts repush --system-id acme01 --from 2026-10-01T09:00 --to 2026-10-01T12:00 \
      --state DELIVERED,UNDELIV --tps 50 --note "customer lost receipts in their outage" --yes  # starts a job, prints its id
fireflo receipts repush status <job-id>                                                     # progress: sent, stored for replay, failed
fireflo receipts repush cancel <job-id>
```

For when a customer's system lost receipts — their outage, a bug on their side, or a bind that stayed
down longer than unpushed receipts are kept — and they ask for them again. The receipts are rebuilt
from the call records: the message id the customer was given when they submitted, the state from the
final outcome, one receipt per part, as the live ones were. Messages with no outcome yet are skipped
and counted. `--include-progress` adds progress receipts.

They are delivered the live way: on the login's sessions if it is bound, otherwise stored and replayed
when it next binds. `--tps` paces the job (default 50, never above the login's own limit) so a re-push
never floods the customer's window. One job per login at a time, at most 31 days per job — the command
splits a longer range into consecutive jobs. A job does not survive a gateway restart; its status says
so, and you rerun with `--from` the last receipt sent.

<Warning>
The customer receives receipts again for messages they may already have closed. A correct SMPP client
treats a repeated receipt for a message id it knows as a no-op; check with them before re-sending a
large range. Each re-sent receipt appears on the message's timeline beside the original, and the job
is recorded as a batch. HTTP customers' callbacks are not re-posted by this command.
</Warning>

### Usage and retention

```bash
fireflo usage rollup [--catch-up]     # summarise cdr_submit into usage_daily
fireflo usage purge                   # delete call records past retention
```

From 0.12.15 `rollup` summarises finished days only (yesterday and back, in the billing zone), and
restates once any line it had written while its day was still open. `purge` also prunes `cdr_event`
and `cdr_rejected` on their own retention keys, after the call-record purge.

<Warning>
`usage purge` **refuses the whole run** if any day it would delete has no rollup, and names the days.
Not a warning — deleting an unsummarised day destroys the consumption record permanently, with nothing
able to reconstruct it. Needs `FIREFLO_CDR_PURGE=true`.

`rollup` is deliberately a separate command. A purge that quietly rolled up first would mean a rollup
bug is discovered by the command that deletes the evidence.
</Warning>

### Connections

```bash
fireflo test-bind <vendor>                      # dial once and report
fireflo disconnect <listener> <session-id>      # drop one bind
fireflo capture start|stop|status <worker> <session-id> [seconds]
fireflo capture txt|pcap <worker> <session-id> > file
```

Session ids come from `fireflo health`. They are the listener's own counter, so they collide between
listeners and restart with the gateway.

<Note>
`disconnect` **ends a connection; it does not withdraw permission.** A healthy client rebinds within
seconds unless you also disable its login.
</Note>

Captures contain message content and destination numbers. They are bounded and held in memory only:
the capture stops itself and is dropped fifteen minutes later, downloaded or not. This replaces turning
on `log.pdus` for a whole worker, which wrote every session's PDUs to a shared log file.

### The seven control verbs

| Verb | Effect |
| :--- | :--- |
| `enable` | Start it now |
| `disable` | Stop it now |
| `suspend` | Stop this worker's own traffic. On a **vendor**, no more messages are sent and the queue is held; on a **listener**, submits are still accepted and charged but parked un-routed, while receipts keep flowing |
| `resume` | Undo `suspend`. A listener routes everything it parked, in arrival order and once each |
| `hold` | On a **listener**, refuse every submit at the door with `ESME_RMSGQFUL` — before any charge — and hold receipts too. On a vendor this is the older stop-sending form; prefer `suspend` there |
| `release` | Undo `hold` |
| `restart` | Bounce a vendor's connection: disable, then enable. Sessions are torn down and re-dialled |

What each does per worker kind is set out in
[Controlling a worker](/platform/operations/worker-control).

### Purging sample data

```bash
fireflo purge seed <traffic-lane|india-dlt|all> [--with-traffic]
fireflo purge --reset-database
```

`purge seed` runs the paired down script and nothing else. There is no search for things that *look
like* test data, because on a configuration database that is how you delete a customer.

`--reset-database` empties every table, back to the state just after `db migrate`. It refuses unless
`FIREFLO_DB_RESET=true`, refuses while the gateway is reachable, and asks you to type the database
name.
