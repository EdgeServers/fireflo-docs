---
title: "Usage and retention"
description: "Call records are deleted on a window. usage_daily is what survives — and the purge refuses to run without it."
---

`cdr_submit` part 1 is the **only** per-message record of what was charged, and it is deleted once it
passes the retention window.

Without a summary that means no statement older than the window can ever be reissued, and the
consumption side of every reconciliation disappears — so every aged account drifts into a discrepancy
nothing can explain.

## `usage_daily` is that summary

One row per account, per product, per **day**.

Daily rather than monthly so that any period is a `SUM` over days — a calendar month, a quarter, an
arbitrary from/to — forever, with no second derived table to disagree with it.

```bash
fireflo usage rollup --catch-up
```

Run it nightly. Running it twice changes nothing that matters.

## Billable figures are final; delivery figures are not

This is what makes the rollup safe to re-run.

| Columns | Stable when | Why |
| :--- | :--- | :--- |
| `price_total`, `cost_total` | **Immediately** | Billing is on `submitted`, which stops moving when the day does |
| Delivery columns | Never quite | Receipts keep arriving |

The rollup is idempotent and restates **only** the delivery columns. A finished day's money is settled
the moment the day ends.

From 0.12.15 the rollup writes **finished days only** — it stops at yesterday in the billing zone, and
`--catch-up` no longer lists the open day as missing. Earlier builds also wrote today's line, and
because the money columns are never restated, a line first written at three in the afternoon kept
that afternoon's totals for good: `usage_daily` under-reported yesterday on any gateway whose rollup
had run during the day. The first rollup after upgrading repairs those lines — a line that was
written before its own day ended is restated in full, once.

## The dashboards read it

From 0.12.15 the control panel's Overview, Usage and Revenue screens, and an account's usage and
reconciliation, read every **whole day** the rollup has summarised from `usage_daily`, and scan the
call records only for the tail: today, plus a day behind the newest summarised line. That is what
keeps a 30-day view answering in under a second at volume, and it is one more reason the nightly
rollup is not optional. A gateway whose rollup has not run reads everything live, as before, and gets
slower as the window grows.

Two figures cannot be read from the summary, because it does not hold them: a summarised day shows
**refused** and **pending revenue** as zero. Today, and the 24-hour range, are always live.

## MT parts

`mt_parts` counts the SMS segments each line's messages were sent as: a three-part message counts
three, and a message every vendor refused counts none. It is what the Billing tab's **MT parts sent**
figures are built from.

It arrived in gateway 0.12.4. **Lines summarised before that hold no count** — empty, not zero, so
nobody mistakes them for a day that sent nothing. A re-run fills them:

```bash
fireflo usage rollup --catch-up
```

Unlike the delivery columns, a re-run never lowers a part count; it can only fill one that is
missing. A day whose call records were already purged cannot be filled and stays uncounted.

## A billing day is a local day

`FIREFLO_BILLING_ZONE` decides where a day starts, and it is read from `app_config` so the rollup and
the panel agree.

<Warning>
**On UTC, the last five and a half hours of an Indian customer's evening land on the next day's
line.** Every daily figure, every month boundary and every invoice is then off by that much traffic.

Set the zone before the first rollup, not after — restating days already summarised means deleting
and recomputing them.
</Warning>

## The purge refuses to delete what nothing has summarised

```bash
FIREFLO_CDR_PURGE=true fireflo usage purge
```

If any day it would delete has **no `usage_daily` row**, it refuses the whole run and names the days.

**Not a warning and not a skip.** Deleting an unsummarised day destroys the consumption record
permanently, and that has to be structurally impossible rather than a matter of running things in the
right order.

<Tip>
`rollup` is deliberately a **separate command**. A purge that quietly rolled up first would mean a
rollup bug is discovered by the command that deletes the evidence.
</Tip>

`FIREFLO_CDR_KEEP_DAYS` sets the window, default **90**.

From 0.12.15 the same run also prunes the two tables the rollup does not cover, because nothing
summarises them: `cdr_event` past `smsg.cdr.event.retention.days` and `cdr_rejected` past
`smsg.cdr.rejected.retention.days`. That happens after the call-record purge and outside its rollup
check, and a failure there is reported without undoing the purge above it. The running gateway's
sweep prunes both on its own schedule anyway; the command is the same work done now, reported, and
available while the gateway is stopped.

## Two windows, two purposes

| Table | Retained by | Losing it costs |
| :--- | :--- | :--- |
| `cdr_submit`, `cdr_final` | `FIREFLO_CDR_KEEP_DAYS`, default 90 | Per-message detail — but not the totals, if the rollup ran |
| `cdr_interim` | `smsg.cdr.interim.retention.days`, default 30 | **A report, not an invoice** — it is vendor quality history |
| `cdr_event` | `smsg.cdr.event.retention.days`, default 90 | The receipt and callback events behind a message's timeline |
| `cdr_rejected` | `smsg.cdr.rejected.retention.days`, default 90 | What the Refused page shows |
| `queue_archive` | `smsg.queue.archive.retention.days`, default 0 (never); or `fireflo queue archive purge` | The detail of what a queue clean archived. Its per-day summary, `queue_archive_summary`, is never deleted |

`cdr_interim` is pruned on its own shorter window precisely because it answers a question about
*recent* traffic: how fast a vendor reports, and whether it reports at all.

## Retention is a partition drop

From 0.12.10 the four large tables (`cdr_submit`, `cdr_final`, `cdr_interim`, `cdr_event`) are
partitioned by calendar month, in UTC. The gateway creates the coming months' partitions itself, and
retention drops whole months in one statement instead of deleting rows: `fireflo usage purge` drops
every month that is entirely past the window (after the same rollup check as before) and deletes
row by row only inside the month the horizon falls in; `cdr_interim` and `cdr_event` are dropped by
month on their own windows by the expiry sweep. A row that arrives outside every month lands in a
default partition rather than failing.

<Warning>
The 0.12.10 upgrade is the one that partitions these tables, and it is the one upgrade a previous
binary cannot run against afterwards: rolling back means restoring the database. The installer says
so and asks before migrating; take the backup it suggests. The migration attaches your existing rows
without copying them, but it builds two indexes over all of them while the gateway is stopped — seconds
on a small install, up to an hour on a hundred million rows.
</Warning>

## A retention policy is not optional

Call records contain **addresses** — they have to, because rating and dispute resolution need them.
If message body recording is on, they contain content as well.

<Warning>
Set a retention policy deliberately rather than inheriting the default. Ninety days of destination
numbers, and possibly of one-time passcodes, exists in every backup you take of that database.
</Warning>

## A working order of operations

<Steps>
  <Step title="Set the billing zone before any traffic">
    It decides where every day boundary falls.
  </Step>
  <Step title="Roll up nightly">
    `fireflo usage rollup --catch-up`, on a schedule.
  </Step>
  <Step title="Verify the rollup covers the window before purging">
    The purge checks this itself and refuses — but knowing it passed is better than discovering it
    refused.
  </Step>
  <Step title="Purge on its own schedule">
    Behind `FIREFLO_CDR_PURGE=true`, which exists so it cannot happen by accident.
  </Step>
</Steps>
