Both directions — delivery receipts out to a `dlr_url`, and MO messages out to a `forward.mo.url` —
share one delivery mechanism, so they share these rules.

## The two rules that decide everything

| Rule | Value |
| :--- | :--- |
| **Success** | HTTP **`200`–`299`**. Anything else is a failure. |
| **Retries** | `smsg.webhook.retries`, default **10**, `smsg.webhook.retry.interval.ms` apart, default **120000** |
| **Timeout** | `smsg.webhook.timeout.ms`, default **5000** — connect *and* request |

<Warning>
**At the default budget, one unreachable endpoint is retried for hours** — ten attempts on a
doubling ladder, two minutes before the first and up to an hour before the last. A customer whose
endpoint is down for an afternoon is not merely missing receipts; every receipt they were owed is
waiting in the gateway for the whole afternoon, and so is every other customer's in the same state.

If you run many customers with unreliable endpoints, lower the retry count before you raise the
store cap below.
</Warning>

## When an endpoint is down for a long time

Without a broker, every receipt or inbound message about to be posted, and every retry waiting out
its backoff, is an entry in one store in memory. From 0.12.15 that store is **bounded**:
`smsg.webhook.retry.pending.max` attempts (10,000 by default, read at startup). Past the cap the
**oldest** waiting attempt is dropped to make room — it has been failing the longest, and the newest
is the likeliest to find its endpoint back.

A drop is never silent. It is counted in `fireflo_webhook_retry_dropped_total`, logged at error once
a minute while it goes on, and for a receipt written to the message's **Customer exchange** as the
attempt it was waiting to make — so a customer asking where a receipt went can be shown the row.
`fireflo_webhook_retry_pending` reports the store's depth; alert on it approaching the cap before the
other counter moves. An endpoint already at its ten-calls-in-flight limit no longer queues attempts
behind it, so one endpoint that has stopped answering costs its own ten slots and nothing else.

<Tip>
A deployment that forwards more receipts than the cap holds during a customer outage wants the
broker, which keeps retries durably and needs no cap. Raising the cap buys memory, roughly a
kilobyte an entry.
</Tip>

## Private addresses are refused

`smsg.webhook.private.targets` is `deny` by default, and from 0.12.15 `deny` means what it should:
loopback, link-local, the RFC 1918 ranges, **carrier-grade NAT** (`100.64/10`), **IPv6 unique-local**
(`fc00::/7`), an IPv4 address carried inside an IPv6 one, and the reserved ranges. Earlier builds
let unique-local and carrier-grade NAT through. Every address a name resolves to is checked, so a
name with one public and one private address is refused, and **a name that does not resolve is
refused too** rather than waved through to fail on its own. A host's verdict is kept for five
seconds, so a burst of receipts to one endpoint is one lookup.

**Batch callbacks go through the same guard** from 0.12.15. The `callback_url` and `errback_url` a
customer gives a batch were the one customer-supplied address the gateway called without checking;
a batch whose callback names a private address or an unresolvable name now gets no callback, and the
refusal is logged.

<Warning>
An install that tested callbacks against a host on its own network — a receiver on the LAN, a
loopback sink — needs `smsg.webhook.private.targets = allow` from 0.12.15, or those callbacks stop
arriving with nothing visible to the customer. Set it knowing it re-opens the gateway's network to
every customer's `dlr_url`; an egress firewall rule for the one host is the better fix.
</Warning>

## A receipt never arrives

<Steps>
  <Step title="Was a dlr_url supplied at all?">
    Over HTTP it must be present and URL-encoded, and `dlr` must be `yes`. Setting one without the
    other does nothing.
  </Step>
  <Step title="Is the endpoint reachable from the gateway host?">
    Not from your laptop — from the host or container the gateway runs on. Egress policy, split DNS
    and private subnets all bite here.
  </Step>
  <Step title="Does it return 200–399?">
    A `401` behind an authenticating proxy is the commonest silent failure. Since 0.11 a `302` to a login
    page, which *does* count as success and swallows the receipt.
  </Step>
  <Step title="Did the gateway log the failure?">
    Forwarding failures and retries are logged. Ten quiet attempts mean the endpoint answered.
  </Step>
  <Step title="What did their endpoint actually say?">
    Open the message in the control panel and read **Customer exchange**. Each callback attempt is a
    row carrying the endpoint, the try number, how long it took and the status.

    Those rows exist only where `smsg.diagnostics` or `smsg.cdr.events` is at least `problems` —
    both are unset on a fresh install, which records nothing. Set one and reproduce if the table is
    empty.

    To see the answer itself rather than only its status code, set `smsg.cdr.events.response =
    excerpt` and reproduce. The **Response** cell then expands to the first 500 characters the
    endpoint returned, which is where a `401` behind a proxy stops looking like a `401` from the
    application.
  </Step>
</Steps>

## The placeholder trap

In `kannel` format, the callback is a **bare `GET` with placeholders substituted — nothing is
appended**.

| Placeholder | Value |
| :--- | :--- |
| `%s` | Gateway message id |
| `%d` | `1` delivered, `2` failed, `4` buffered, `8` submitted to SMSC |

```json
{ "dlr_url": "https://example.com/dlr?msgid=%s&status=%d" }
```

<Warning>
**A URL with no placeholders receives a request carrying nothing at all** — no body, no query, no
identifier. The endpoint is hit on schedule, returns `200`, and the customer concludes receipts are
"working but empty".

This is the single most common receipt integration mistake, and nothing in the system flags it: an
empty callback is indistinguishable from a correctly configured one that happens to carry no data.
</Warning>

## MO forwards never arrive

MO callbacks are **`POST`**, and the same `200`–`299` and retry rules apply.

- `forward.mo.url` is set on the SMPP client worker **receiving** the MO — not on the listener, and
  not globally.
- `forward.mo.format` is `JSON` or `FORM`.
- The URL may carry placeholders, URL-encoded before replacement:

| Placeholder | Value |
| :--- | :--- |
| `%p` | Originating address (`from`) |
| `%P` | Destination address (`to`) |
| `%a` | Message text |
| `%t` | Timestamp |
| `%i` | Inbound gateway identifier |
| `%I` | Message centre |
| `%o` | Data coding value |

```properties
outSms.instance.testRoute.forward.mo.url = https://example.com/mo?from=%p&to=%P&text=%a
```

<Tip>
Full inbound MO detail needs `print.mos = true` **temporarily**. Treat that output as sensitive — it
contains message content and both addresses.
</Tip>

## Receipts that arrive but say the wrong thing

Not a delivery problem, and worth ruling out before you go looking at the network:

- **`request.dlrs` is off on the vendor.** Every message then settles as `EXPIRED` at the deadline,
  because nothing ever reports an outcome. The delivery rate becomes *meaningless* rather than zero —
  which is worse, since a zero looks like a problem and a meaningless number looks like data.
- **A level 1 receipt is not the outcome.** `ACCEPTD` and `BUFFRED` both arrive as level 1 and another
  receipt follows. A client that treats the first receipt as final will report the wrong thing
  forever.
- **Three segments, three receipts.** `conf.dlr.multipart` defaults to `all`, so a customer gets one
  receipt per `submit_sm` they sent. `first` or `last` collapses that to one.
