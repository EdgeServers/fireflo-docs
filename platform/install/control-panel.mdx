The control panel serves both the operator screens and the customer portal. It is a separate process
with its own installer and its own environment file.

<Note>
**Install it after the gateway.** The gateway owns the database schema; the panel only reads and writes
rows in it.

It is **not on the message path** — a panel that is down costs you the ability to make changes, not the
ability to send.
</Note>

## Install

```bash
./scripts/fireflo-panel-install check
sudo ./scripts/fireflo-panel-install install
```

`install` does Node, service user, directories, source, `npm ci`, build, environment, systemd unit, and
then checks that it answers. It asks for what it needs first and changes nothing until you agree.

**A host without Node is fine for `install`**: it adds Node 22 from NodeSource itself. `check` still
reports a missing Node as a failure, because on its own it installs nothing; so does `install
--no-packages`.

## What it derives

Given the gateway's configuration directory, the installer reads out the **operational tokens** and the
**read-only database connection** rather than asking you to copy them by hand.

<Warning>
**`--config-url` is never derived.** The read-write connection to the configuration tables is the one
that can change what customers are charged, so it is always given explicitly.

Without it the panel reports every configuration domain as **not editable**, rather than failing at
the first save.
</Warning>

## Operators and admins

Operators and admins are rows in the gateway's database. Create the first admin on the gateway and
add the rest from the panel's **Users** page:

```bash
fireflo user add --email you@example.com --role admin --generate
```

`OPERATOR_USERNAME` / `OPERATOR_PASSWORD` in `panel.env` are a deprecated fallback, honoured only
while no admin or operator row exists and removed in 0.13; `fireflo-panel-install passwd` still rolls
that one account — see [`passwd`](/reference/cli/fireflo-panel-install#why-passwd-exists-as-a-verb).

**From 0.12.15 a password change signs that user's other browsers out.** An admin's reset on the Users
page, the person's own change, and `fireflo user passwd` on the gateway all count: every session
signed in before the change is refused on its next request, and the browser that made its own change
stays signed in. The upgrade itself signs nobody out. `--rotate-secret` remains for the other case, a
suspected compromise of the session secret, and signs out every user at once.

**Changing the licence is an admin's job** from 0.12.15. Activating, the two offline halves and
releasing answer an operator as if the route did not exist; an operator still sees the licence state
on `/cp/verify` and can press **Check again**.

## What the panel writes down

From 0.12.15 **every configuration change leaves a `config_changed` row in the Access log** — logins,
routing tables and rules, vendors and listeners and their live controls, filters, groups, TLV
definitions, products, pricing, whitelist policies and rows, balances and top-ups, statement closes,
exports, reloads, disconnects and lifted holds. Each carries what it was and what it became, with
secrets reported only as present or absent, and a change scoped to an account also appears in that
account's activity history. On a database the gateway's 0.12.15 migrations have not reached, the row
is skipped with one console line and the panel's log file still has it.

## The two URLs that are easy to swap

| Variable | Points at | If you get it wrong |
| :--- | :--- | :--- |
| `GATEWAY_OPS_URL` | The **management** port, 9000 | Live health reads 404 on everything |
| `GATEWAY_API_URL` | The **messaging** port, 8080 | Every playground call 404s |

They are different ports carrying different things and sharing no paths. Both failures look like an
outage and are not.

## TLS in front

The panel speaks plain HTTP on `PORT` (3000 by default). Put nginx or similar in front of it, and set
`AUTH_URL` to the public origin — unset, a sign-out redirects to localhost.

Tell the panel how many proxies sit in front of it with `TRUSTED_PROXY_HOPS` (the installer writes
`1`). Since 0.12.14 the panel reads a client's address from `X-Forwarded-For` only when this is set;
without it every sign-in, lockout and fail2ban entry is recorded with no address, and a panel reached
directly cannot be fed a forged address. Pass `X-Forwarded-For`, `X-Forwarded-Proto` and `Host`
through from the proxy.

Every response carries `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and
`X-Content-Type-Options: nosniff`; with `AUTH_COOKIE_SECURE=true` it also sends HSTS for a year, so
turn that on only once the panel is served over TLS for good.

**`AUTH_URL` is also the origin every write is checked against.** From 0.12.15 a request that would
change something — any `POST`, `PUT`, `PATCH` or `DELETE` under `/api/control` or `/api/mis` — whose
`Origin` header names a different origin than `AUTH_URL` is refused with `403` before the route runs;
reads, and requests that carry no `Origin` such as scripts, are untouched. The consequence worth
knowing: **a panel opened at an address other than its `AUTH_URL`** — the server's IP while the DNS
name is being set up, say — **can read everything and change nothing.** The error says both addresses
and what to set, so it is not a mystery when it happens. With `AUTH_URL` unset the request's own host
is the reference instead, and no operator sign-in link is emailed at all, because the request's host
header is not trusted enough to put in a mail.

**The SMPP client test tool reaches only this gateway's own hosts.** It binds from the panel's process
with a login's stored password, so from 0.12.15 it will dial only hosts it already knows as the
gateway's — the hosts in `GATEWAY_OPS_URL` and `GATEWAY_API_URL`, `FIREFLO_PUBLIC_HOST`, each
listener's public host, and `SMPP_TEST_HOST`. A gateway reached through a load balancer under another
name goes in `SMPP_TEST_ALLOWED_HOSTS`, comma or space separated; anything else typed into **Other
host:port** is refused with a sentence naming that variable.

`NODE_ENV=production` is set for the **build** as well as the run, because it decides whether the
session cookie is marked secure.

## Customer sign-in needs mail

A customer signs in through a magic link. With `FIREFLO_SMTP_HOST` or `FIREFLO_SMTP_FROM` unset, **no
customer can sign in at all** — the portal says the link cannot be sent rather than failing silently,
but nobody gets in.

See [Portal access](/platform/customers/portal-access).

## Upgrading

```bash
sudo ./scripts/fireflo-panel-install update
```

Replaces the build. **Never touches the environment file.**

<Warning>
Upgrade the panel and the gateway **together**. The panel's version repeats the gateway release it was
built against in its first three numbers — `0.7.3.1` pairs with gateway `0.7.3` — and it checks the
pair at runtime and says so when they disagree.
</Warning>

## Under a virtualhost

`--tenant NAME` puts the panel at `/srv/fireflo/NAME/panel` as unit `fireflo-NAME-panel`, and the same
word names the same instance to the gateway installer. With `--vhost PATH` the root moves to
`PATH/panel`, with the gateway at `PATH/gateway`.

<Warning>
Under `--vhost`, `CDR_EXPORT_DIR` must sit inside a `BindPaths=` root. **That failure is silent** —
exports are prepared and then cannot be read.
</Warning>

Every variable is at [Control panel environment](/reference/config/control-panel).
