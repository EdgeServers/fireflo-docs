---
title: "Adding one more tenant"
description: "The whole recipe, in order, for a second customer on a host that already runs one: name, ports, database, both installers, TLS, and the first message."
---

[Several instances](/platform/install/multiple-instances) explains the mechanism — one `--tenant` word
naming the same instance to both installers, and what `--vhost` buys. This page is the same information
assembled into one run, for the moment you actually have a second customer to add.

**Nothing here is shared with the tenants already on the host** except the packages, Java, Node and
PostgreSQL themselves — see [What each instance needs of its
own](/platform/install/multiple-instances#what-each-instance-needs-of-its-own). A new tenant gets its
own database, its own ports, its own operational tokens and its own service account choice.

<Steps>
  <Step title="Pick the name and the layout">
    One word, used **identically** on both installers — it is what lets `update` find the right
    instance later without you re-typing paths.

    ```bash
    TENANT=acme
    ```

    Two layouts, pick one:

    | | Command | Path |
    | :--- | :--- | :--- |
    | Flat (default) | `--tenant $TENANT` | `/srv/fireflo/$TENANT/{gateway,panel}` |
    | Virtualhost | `--tenant $TENANT --vhost /home/$TENANT --user $TENANT` | `/home/$TENANT/{gateway,panel}` |

    Reach for `--vhost` when the tenant's own SSH or SFTP account already lives under `/home` — it is
    what isolates the gateway from that account's files, not just a different path. See [A
    virtualhost](/platform/install/multiple-instances#a-virtualhost).

    <Warning>
    **Under `--vhost`, `--user` is not optional.** A home directory is `0750` and owned by its own
    account, and the installer **deliberately will not chown a directory that already exists** — so a
    service running as any other account cannot traverse it.

    The failure is late and reads as something else: the panel dies at `npm ci` with
    `can't cd to /home/<name>/panel/app`, and the gateway starts and then cannot reach its own
    configuration. `ProtectHome=tmpfs` and `BindPaths=` make the directory *visible* inside the unit's
    namespace; neither changes a permission bit.

    Pass the account that owns the virtualhost, on **both** installers.
    </Warning>

    <Warning>
    **`--vhost` without `--tenant` means something else.** Alone, it keeps a legacy flat layout —
    `PATH/{app,conf,data}` — rather than `PATH/panel`. That form exists so panels installed before
    `--tenant` keep working, and for a new tenant it silently puts the gateway and the panel in
    different layouts. Always give both flags together.
    </Warning>
  </Step>

  <Step title="Reserve ports">
    Every existing tenant on the host already holds an SMPP port, an HTTP port and an ops port. Pick a
    band the new one cannot collide with:

    ```bash
    --smpp-port-range 27801-27824 --http-port 8081 --ops-port 9001
    ```

    <Warning>
    `--ops-port` is **never** opened in the firewall regardless of what you pass — it binds loopback
    only. `--http-port` is what a customer's ESME or REST client actually reaches, so it is the one to
    check against `ufw status` before choosing it.
    </Warning>
  </Step>

  <Step title="Its own database">
    One tenant, one database — never a schema shared with another tenant's rows.

    ```bash
    sudo -u postgres createuser fireflo_$TENANT --pwprompt
    sudo -u postgres createdb fireflo_$TENANT --owner fireflo_$TENANT
    ```

    A separate role per tenant is not required — one `fireflo` role can own several databases — but it
    means a leaked credential for one tenant cannot read another's. See [The
    database](/platform/install/database).
  </Step>

  <Step title="Install the gateway">
    ```bash
    sudo ./scripts/fireflo-install install --tenant $TENANT \
      --smpp-port-range 27801-27824 --http-port 8081 --ops-port 9001 \
      --db-name fireflo_$TENANT --db-user fireflo_$TENANT --db-password-file /root/.acme-db-pw \
      --config-source db --bootstrap \
      --country Australia --country-code 61 --product standard --rate 0.0450 --currency AUD
    ```

    Under the virtualhost layout, add `--vhost /home/$TENANT --user $TENANT` — both, per the warnings
    in step 1.

    It asks first and shows you every decision before writing anything — add `--yes` only once you
    trust the answer it would print. `--bootstrap` writes the least a fresh database needs: a `default`
    routing table, an empty `MESSAGE` table, one SMPP listener, one login. Its generated password
    prints **once**; capture it.

    <Note>
    Flags take **space-separated** values. `--vhost=/home/$TENANT` is rejected as an unknown option
    rather than parsed, on both installers.
    </Note>

    <Warning>
    **`--bootstrap` only on a genuinely empty database.** It refuses the moment it finds a routing
    table, a worker or a login — so reinstalling a gateway whose database already exists needs
    `--config-source db` on its own. Passing it the wrong way round is how an install ends up either
    refusing halfway or starting with nothing to route to.
    </Warning>

    Full flag list at [`fireflo-install`](/reference/cli/fireflo-install).
  </Step>

  <Step title="Verify before adding anything">
    ```bash
    cd /srv/fireflo/$TENANT/gateway   # or the --vhost path
    scripts/fireflo verify
    ```

    <Note>
    **Exit code 4** here is expected and correct: the deployment is sound, it simply has nothing to
    route to yet. It becomes 0 once a vendor and a rule exist, in the next step's follow-on — see
    [First configuration](/platform/install/first-configuration).
    </Note>
  </Step>

  <Step title="Install the panel">
    ```bash
    sudo ./scripts/fireflo-panel-install install --tenant $TENANT --port 3001 \
      --gateway-conf-dir /srv/fireflo/$TENANT/gateway/conf \
      --public-url https://acme-panel.example.com \
      --operator acme-admin
    ```

    Under the virtualhost layout, add `--vhost /home/$TENANT --user $TENANT` and point
    `--gateway-conf-dir` at `/home/$TENANT/gateway/conf`. **Install the panel after the gateway** — it
    reads that directory.

    <Warning>
    **`--port` is never derived from `--tenant`.** It stays `3000` unless given explicitly, so a
    second panel on the same host needs its own or the installer refuses rather than overwrite the
    first tenant's unit.
    </Warning>

    Three things it works out for itself from `--gateway-conf-dir`: both operational tokens, the
    read-only `METRICS_DATABASE_URL`, and the ops URL — which it builds from that gateway's recorded
    `FIREFLO_OPS_PORT`, so a non-default `--ops-port` needs no second flag here.

    <Warning>
    `--config-url` is never derived, on purpose — it is the connection that can change what a customer
    is billed. Without it the panel comes up read-only for this tenant.

    It is left off the command above deliberately: passed as a flag, the database password lands in
    your shell history and in `ps` output. Omit it and the installer prompts instead — and that prompt
    accepts the literal word **`same`**, meaning "reuse the connection just derived from the gateway",
    which is the right answer whenever one role owns the tenant's database.
    </Warning>
  </Step>

  <Step title="TLS in front, one origin per tenant">
    The panel speaks plain HTTP on `--port` (default 3000, and it must be **unique per tenant** on a
    shared host — pass one explicitly for every tenant after the first). Put nginx or equivalent in
    front, terminating TLS at a hostname of this tenant's own:

    ```nginx
    server {
        listen 443 ssl;
        server_name acme-panel.example.com;
        location / {
            proxy_pass http://127.0.0.1:3001;   # this tenant's --port
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```

    `--public-url` above must match `server_name` exactly — it is written as `AUTH_URL`, and without it
    a sign-out redirects to `localhost` regardless of what the proxy forwards. See [TLS in
    front](/platform/install/control-panel#tls-in-front).
  </Step>

  <Step title="Finish the configuration">
    `bootstrap` deliberately leaves out a vendor and a rate — nobody else can guess a vendor's
    credentials, and an invented price bills silently where an absent one shows up unpriced. Add both,
    then a routing rule naming the vendor, then this tenant's first customer login — in that order, and
    why, at [First configuration](/platform/install/first-configuration).
  </Step>

  <Step title="Send one, as a customer would">
    ```bash
    FIREFLO_SEND_LOGIN=... FIREFLO_SEND_PASSWORD=... \
      scripts/fireflo send AcmeBrand 61400000000 "first message"
    ```

    A `200` means accepted, charged and queued — watch the call record in this tenant's panel for the
    delivery outcome.
  </Step>
</Steps>

## What is genuinely new versus shared

| | This tenant | The host |
| :--- | :--- | :--- |
| Database | New, own schema | — |
| Ports (SMPP, HTTP, ops, panel) | New, non-overlapping | — |
| Operational tokens | Generated fresh by this install | — |
| Service account | **Required** under `--vhost` (`--user`); optional otherwise | Shareable only outside a virtualhost |
| Packages, Java, Node, PostgreSQL server | — | Already installed |

## Undoing this

There is no `uninstall` verb, and a tenant is four systemd units rather than two — the gateway's
`-logclean.timer` outlives a careless removal and keeps firing at a deleted log directory. The full
procedure, and what it deliberately leaves alone, is at [Removing a
tenant](/platform/install/multiple-instances#removing-a-tenant).
