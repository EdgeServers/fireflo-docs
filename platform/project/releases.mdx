FireFlo uses standard semantic versioning. What matters to you is what a version number promises and
what to check before you take one.

## What the number means

| Change | Means |
| :--- | :--- |
| **Major** — `1.0.0` → `2.0.0` | A breaking change. Expect to read the notes and to change something. |
| **Minor** — `0.7.0` → `0.8.0` | New capability. Existing behaviour is intended to survive, but **defaults can move** — see below. |
| **Patch** — `0.7.3` → `0.7.4` | A fix. The safest kind to take, and usually the reason to take it promptly. |

Your release notes accompany each build. They are the authoritative list of what changed; this page is
about what to look for in them.

Two things the table will not tell you on its own.

**The control panel column shows the newest revision for that gateway release.** The fourth number is
a panel-only revision and moves on its own — 0.7.3 had three of them. Any panel version whose first
three numbers match the gateway is a valid pair; the panel checks this at runtime and says so when it
does not.

**Five gateway releases inside two days is not a mistake.** 0.7.0 opened a piece of billing work, and
each release after it closed something the previous one exposed — a segment billing defect, then the
template matching it depended on, then the placeholder grammar, then the postpaid work, then three
defects on the credit path. Releases cluster when a seam is being worked; that is what it looks like.

## Before you upgrade

The pattern worth internalising: **the changes that hurt are the quiet ones.** A breaking API change
announces itself; a changed default does not.

<AccordionGroup>

<Accordion title="Read the release notes for changed defaults">
A default that moves changes behaviour on every deployment that never set the value — which is most
of them. These are the entries to read closely, more than the new features.
</Accordion>

<Accordion title="Check whether anything moved between ports">
Enabling the management port **moved** `/q/metrics` from 8080 to 9000. A Prometheus job still pointed
at the old one gets `404`s rather than failing loudly, so a dashboard reads as a quiet system rather
than a broken monitor.
</Accordion>

<Accordion title="Check whether a database migration is included">
Migrations are **forward-only**. There is no down-migration, so the rollback path is a restore rather
than a reverse migration — take the backup before, not after.
</Accordion>

<Accordion title="Check whether receipt behaviour changed">
Receipt semantics have changed twice in ways that were invisible until a customer noticed. `level`
used to always read `2`, so `ACCEPTD` was reported as an outcome; and the `User-Agent` on webhook
calls changed from the JDK default to `FireFlo/<version>`, which matters to any receiver with an
allow-list.
</Accordion>

<Accordion title="Decide whether a customer notice is needed">
If figures a customer can see will change, they need telling before it happens — with the number, the
direction and the date. See [Customer notices](/platform/migrating/customer-notices).
</Accordion>

</AccordionGroup>

## Version pairing

The gateway publishes its running version on `/ops/health`, and the control panel shows both its own
and the gateway's.

<Warning>
**A mismatched pair is flagged deliberately.** The panel degrades rather than breaking when it talks
to an older gateway — a column simply drops out of its queries — but a feature that appears absent
because of a version gap looks exactly like a feature that is broken.

Check the pair before investigating anything that "should be there and isn't".
</Warning>

## Reporting problems

Everything goes to [support@fireflo.au](mailto:support@fireflo.au). What changes is how you frame it:

| | Include |
| :--- | :--- |
| **A reproducible bug** | The version pair, what you did, what happened, and one message serial that shows it |
| **A question or setup help** | What you are trying to achieve, not only the error — the answer is often a different approach |
| **Anything security-sensitive** | **Say so in the subject.** Do not attach unredacted logs or configuration to a first mail; we will tell you where to send them |

<Warning>
**Redact before sharing.** Credentials, system IDs, IP addresses, phone numbers and message content
all appear in configuration and logs. `fireflo` redacts what it can; a hand-copied log line is your
own responsibility.
</Warning>
