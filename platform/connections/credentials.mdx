title: "Logins and credentials"
description: "How a customer authenticates, why the account rather than the login is the billing key, and the two fields whose defaults point opposite ways."
---

A **login** is one way to authenticate. An **account** is what gets billed. One account may hold
several logins, and that relationship is load-bearing.

## Why the account, not the login

Rate ceilings, prepaid balance, credit limits and statements are all keyed on the **account**.

<Note>
A per-login limit would let a customer raise their own ceiling by creating another login. Keying on the
account is what makes the limit mean something.
</Note>

## The two protocols authenticate differently

| | SMPP | HTTP |
| :--- | :--- | :--- |
| Requires | `systemId` **and** `password` | `apiKey`, **or** `systemId` + `password` |
| Lookup key | `systemId` | `apiKey` if present, otherwise `systemId` |
| Sent as | The bind request | HTTP Basic — the Basic username is the lookup key |

<Warning>
**For the REST API, set both `systemId` and `password`.** A credential holding only an `apiKey` is
valid configuration and **cannot authenticate** — it is refused with `403`.
</Warning>

## Two fields, opposite defaults

| Field | Empty means |
| :--- | :--- |
| `allowedIps` | **No restriction** |
| `allowedProducts` | **Refuse the `product` field outright** |

Deliberate. The product selects the rate, so a login that could name any product could pick its own
price. Naming one it has not been granted is refused rather than permitted by omission.

### Locking a login to its first address

**Lock SMPP logins to their first address** (`smsg.smpp.whitelist.first.bind`, off by default, on the
control panel's Gateway page under *SMPP logins*) closes the "no restriction" default for SMPP. With
it on, the first successful bind by a login whose `allowedIps` is empty saves that bind's exact
address as the login's only allowed one, and later binds from anywhere else are refused.

- It takes effect at once, before the gateway's next configuration poll, and on a cluster the first
  node to save wins — a bind from a different address that loses the race is refused.
- A login that already has addresses is never changed. Clearing a login's list re-arms it: the next
  bind locks it again.
- REST logins are not affected, and it needs logins kept in the database — with
  `credentials.yml` it does nothing.

<Warning>
**Switching it on applies to existing logins too**, at their next bind. Before you turn it on, check
that none of your customers binds one login from more than one address — the second address would be
refused from then on.
</Warning>

### Seeing who is connected

On an account's **Logins** tab, each SMPP login shows whether it is bound right now, and if so how
many sessions it holds — split into transmitter (TX), receiver (RX) and transceiver (TRX) — against
the login's own limits, where it connects from, and how long the oldest session has been up. It
refreshes every ten seconds. The count is of that exact system ID on every listener; a login's own
limits apply on each listener separately, so the panel checks them against the busiest one.

### Re-sending receipts

From 0.12.19 an admin can re-send an SMPP login's delivery receipts for a period, from **Re-send
receipts…** on the login's card — for a customer whose system lost them in its own outage, or whose bind
stayed down longer than unpushed receipts are kept. Choose the period (at most 31 days), which outcomes,
whether to include progress receipts, a rate (50 a second by default, never above the login's own
limit) and a note. **Check what would be sent** answers how many receipts for how many messages,
whether the login is bound right now, and roughly how long it will take; messages with no outcome yet
are skipped and counted.

The receipts are rebuilt from the call records with the message ids the customer was given at submit,
and sent the way live ones are: on the login's sessions if it is bound, otherwise stored and replayed
when it next binds. The job runs on the gateway — the dialog shows its progress and can cancel it, and
reopening the dialog resumes the progress bar — and each finished job is listed on
[Reports → Archives → Batches](/platform/control-panel/archives). The command line equivalent is
`fireflo receipts repush`.

<Warning>
The customer receives receipts again for messages they may already have closed. A correct SMPP client
treats a repeated receipt for a message id it knows as a no-op, but agree it with them before
re-sending a large period.
</Warning>

## Rotating a secret

A customer rotates their own from the portal, and the new secret is shown **exactly once**. An operator
can also do it from the account page.

<Warning>
**Disabling a login drops its live binds.** That is the intended behaviour — otherwise a revoked
credential keeps sending until the session happens to drop — but it means disabling one during
business hours interrupts traffic immediately.
</Warning>

## Default TLVs on a credential

Values supplied on the customer's behalf when their `submit_sm` does not carry them.

```yaml
defaultTlvs:
  peid_0x1400: "1101234567890123456"
  acct_0x1403: "MESSAGE:owner_id"
```

Applied **after** the tags on the message — a value the customer sent always wins — and **before** the
listener's `mandatory.tlvs.submit` check, so a credential can satisfy a required tag on behalf of a
client that never sends one.

<Warning>
**Credential TLV defaults are snapshotted at bind.** Unlike routing and properties, editing them
applies on that client's **next bind**, not to sessions already connected.
</Warning>

The grammar, and why `1400` and `0x1400` are different tags, is at
[TLV declarations](/reference/smpp/tlvs).

## Where credentials live

| Mode | Source |
| :--- | :--- |
| File | `credentials.yml`, hot reloaded within ~200 ms |
| Database | `app_credential`, applied within one poll interval |

<Warning>
Switching to `db` against an **empty** `app_credential` refuses every bind and every REST call at
once. The loader publishes the empty map rather than falling back to the file.

`fireflo import credentials` refuses unconditionally when it would yield no usable credential, flag or
no flag — that refusal exists precisely to prevent this.
</Warning>

## Unknown keys are warned, not rejected

So a newer configuration loads on an older build. **A typo is silently dropped** — read the log after
editing if a field appears to have no effect.

## What a customer sees of their own

From the portal: their logins, where to send, and a rotate button. Never another account's, and never a
secret they did not just create. See [Portal access](/platform/customers/portal-access).
