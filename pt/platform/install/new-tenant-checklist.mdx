---
title: "Adicionando mais um tenant"
description: "A receita completa, em ordem, para um segundo cliente em um host que já roda um: nome, portas, banco de dados, ambos os instaladores, TLS e a primeira mensagem."
---

[Várias instâncias](/platform/install/multiple-instances) explica o mecanismo — uma palavra `--tenant`
nomeando a mesma instância para ambos os instaladores, e o que `--vhost` traz. Esta página é a mesma
informação organizada em uma única execução, para o momento em que você realmente tem um segundo
cliente para adicionar.

**Nada aqui é compartilhado com os tenants já existentes no host** exceto os próprios pacotes, Java,
Node e PostgreSQL — veja [O que cada instância precisa ter só para
si](/platform/install/multiple-instances#what-each-instance-needs-of-its-own). Um novo tenant recebe
seu próprio banco de dados, suas próprias portas, seus próprios tokens operacionais e a sua própria
escolha de conta de serviço.

<Steps>
  <Step title="Escolha o nome e o layout">
    Uma palavra, usada **identicamente** em ambos os instaladores — é o que permite ao `update`
    encontrar a instância correta depois, sem você redigitar caminhos.

    ```bash
    TENANT=acme
    ```

    Dois layouts, escolha um:

    | | Comando | Caminho |
    | :--- | :--- | :--- |
    | Plano (padrão) | `--tenant $TENANT` | `/srv/fireflo/$TENANT/{gateway,panel}` |
    | Virtualhost | `--tenant $TENANT --vhost /home/$TENANT --user $TENANT` | `/home/$TENANT/{gateway,panel}` |

    Recorra a `--vhost` quando a conta SSH ou SFTP do próprio tenant já mora sob `/home` — é o que
    isola o gateway dos arquivos daquela conta, não apenas um caminho diferente. Veja [Um
    virtualhost](/platform/install/multiple-instances#a-virtualhost).

    <Warning>
    **Sob `--vhost`, `--user` não é opcional.** Um diretório home é `0750` e pertence à sua própria
    conta, e o instalador **deliberadamente não fará chown de um diretório que já existe** — portanto
    um serviço rodando com qualquer outra conta não consegue atravessá-lo.

    A falha é tardia e se apresenta como outra coisa: o painel morre no `npm ci` com
    `can't cd to /home/<name>/panel/app`, e o gateway inicia e depois não consegue alcançar a sua
    própria configuração. `ProtectHome=tmpfs` e `BindPaths=` tornam o diretório *visível* dentro do
    namespace da unidade; nenhum dos dois muda um bit de permissão.

    Passe a conta dona do virtualhost em **ambos** os instaladores.
    </Warning>

    <Warning>
    **`--vhost` sem `--tenant` significa outra coisa.** Sozinha, ela preserva um layout plano legado
    — `PATH/{app,conf,data}` — em vez de `PATH/panel`. Essa forma existe para que painéis instalados
    antes de `--tenant` continuem funcionando, e para um tenant novo ela silenciosamente coloca o
    gateway e o painel em layouts diferentes. Sempre passe as duas flags juntas.
    </Warning>
  </Step>

  <Step title="Reserve portas">
    Cada tenant existente no host já ocupa uma porta SMPP, uma porta HTTP e uma porta ops. Escolha
    uma faixa em que o novo não possa colidir:

    ```bash
    --smpp-port-range 27801-27824 --http-port 8081 --ops-port 9001
    ```

    <Warning>
    `--ops-port` **nunca** é aberta no firewall, independentemente do que você passar — ela faz bind
    apenas em loopback. `--http-port` é a que o ESME ou cliente REST do cliente realmente alcança,
    então é a que você deve conferir contra `ufw status` antes de escolher.
    </Warning>
  </Step>

  <Step title="Seu próprio banco de dados">
    Um tenant, um banco — nunca um schema compartilhado com as linhas de outro tenant.

    ```bash
    sudo -u postgres createuser fireflo_$TENANT --pwprompt
    sudo -u postgres createdb fireflo_$TENANT --owner fireflo_$TENANT
    ```

    Uma role separada por tenant não é obrigatória — uma role `fireflo` pode ser dona de vários
    bancos — mas isso significa que uma credencial vazada de um tenant não pode ler as de outro.
    Veja [O banco de dados](/platform/install/database).
  </Step>

  <Step title="Instale o gateway">
    ```bash
    sudo ./scripts/fireflo-install install --tenant $TENANT \
      --smpp-port-range 27801-27824 --http-port 8081 --ops-port 9001 \
      --db-name fireflo_$TENANT --db-user fireflo_$TENANT --db-password-file /root/.acme-db-pw \
      --config-source db --bootstrap \
      --country Australia --country-code 61 --product standard --rate 0.0450 --currency AUD
    ```

    Sob o layout de virtualhost, acrescente `--vhost /home/$TENANT --user $TENANT` — ambos, conforme
    os avisos do passo 1.

    Ele pergunta antes e mostra cada decisão antes de escrever qualquer coisa — acrescente `--yes`
    apenas quando você confiar na resposta que ele imprimiria. `--bootstrap` escreve o mínimo que um
    banco novo precisa: uma tabela de roteamento `default`, uma tabela `MESSAGE` vazia, um listener
    SMPP, um login. A senha gerada é impressa **uma única vez**; capture-a.

    <Note>
    Flags aceitam valores **separados por espaço**. `--vhost=/home/$TENANT` é rejeitado como opção
    desconhecida em vez de ser interpretado, em ambos os instaladores.
    </Note>

    <Warning>
    **`--bootstrap` apenas em um banco genuinamente vazio.** Ele recusa no momento em que encontra
    uma tabela de roteamento, um worker ou um login — então reinstalar um gateway cujo banco já
    existe precisa apenas de `--config-source db`. Passar as flags de forma invertida é como uma
    instalação acaba ou recusando no meio do caminho ou iniciando sem ter para onde rotear.
    </Warning>

    Lista completa de flags em [`fireflo-install`](/reference/cli/fireflo-install).
  </Step>

  <Step title="Verifique antes de adicionar qualquer coisa">
    ```bash
    cd /srv/fireflo/$TENANT/gateway   # ou o caminho de --vhost
    scripts/fireflo verify
    ```

    <Note>
    **Código de saída 4** aqui é esperado e correto: a implantação está sólida, ela simplesmente
    ainda não tem para onde rotear. Torna-se 0 assim que um fornecedor e uma regra existirem, no
    próximo passo — veja [Primeira configuração](/platform/install/first-configuration).
    </Note>
  </Step>

  <Step title="Instale o painel">
    ```bash
    sudo ./scripts/fireflo-panel-install install --tenant $TENANT --port 3001 \
      --gateway-conf-dir /srv/fireflo/$TENANT/gateway/conf \
      --public-url https://acme-panel.example.com \
      --operator acme-admin
    ```

    Sob o layout de virtualhost, acrescente `--vhost /home/$TENANT --user $TENANT` e aponte
    `--gateway-conf-dir` para `/home/$TENANT/gateway/conf`. **Instale o painel depois do gateway** —
    ele lê esse diretório.

    <Warning>
    **`--port` nunca é derivado de `--tenant`.** Permanece em `3000` a menos que seja informada
    explicitamente, então um segundo painel no mesmo host precisa da sua própria, senão o instalador
    recusa em vez de sobrescrever a unidade do primeiro tenant.
    </Warning>

    Três coisas que ele descobre por si próprio a partir de `--gateway-conf-dir`: ambos os tokens
    operacionais, a `METRICS_DATABASE_URL` somente leitura e a URL de ops — que ele constrói a partir
    do `FIREFLO_OPS_PORT` registrado desse gateway, então uma `--ops-port` não-padrão não requer uma
    segunda flag aqui.

    <Warning>
    `--config-url` nunca é derivada, propositalmente — é a conexão que pode alterar o que é cobrado
    de um cliente. Sem ela, o painel sobe em modo somente leitura para este tenant.

    Ela foi deliberadamente omitida do comando acima: passada como flag, a senha do banco parou no
    seu histórico de shell e na saída do `ps`. Omita-a e o instalador pergunta — e esse prompt
    aceita a palavra literal **`same`**, significando "reutilize a conexão recém-derivada do
    gateway", que é a resposta certa sempre que uma única role for dona do banco do tenant.
    </Warning>
  </Step>

  <Step title="TLS na frente, uma origem por tenant">
    O painel fala HTTP simples em `--port` (padrão 3000, e deve ser **único por tenant** em um host
    compartilhado — passe uma explicitamente para cada tenant depois do primeiro). Coloque nginx ou
    equivalente na frente, terminando TLS em um hostname próprio deste tenant:

    ```nginx
    server {
        listen 443 ssl;
        server_name acme-panel.example.com;
        location / {
            proxy_pass http://127.0.0.1:3001;   # a --port deste tenant
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```

    O `--public-url` acima deve casar exatamente com `server_name` — é escrito como `AUTH_URL`, e sem
    ele um sign-out redireciona para `localhost` independentemente do que o proxy encaminhe. Veja
    [TLS na frente](/platform/install/control-panel#tls-in-front).
  </Step>

  <Step title="Finalize a configuração">
    O `bootstrap` deliberadamente deixa de fora um fornecedor e uma tarifa — ninguém mais pode
    adivinhar as credenciais de um fornecedor, e um preço inventado cobra silenciosamente enquanto
    um ausente aparece sem preço. Adicione ambos, depois uma regra de roteamento nomeando o
    fornecedor, e então o primeiro login de cliente deste tenant — nessa ordem, e por que, em
    [Primeira configuração](/platform/install/first-configuration).
  </Step>

  <Step title="Envie uma, como faria um cliente">
    ```bash
    FIREFLO_SEND_LOGIN=... FIREFLO_SEND_PASSWORD=... \
      scripts/fireflo send AcmeBrand 61400000000 "first message"
    ```

    Um `200` significa aceito, cobrado e enfileirado — observe o registro de chamada no painel deste
    tenant para o desfecho da entrega.
  </Step>
</Steps>

## O que é realmente novo versus compartilhado

| | Este tenant | O host |
| :--- | :--- | :--- |
| Banco de dados | Novo, schema próprio | — |
| Portas (SMPP, HTTP, ops, painel) | Novas, sem sobreposição | — |
| Tokens operacionais | Gerados novos por esta instalação | — |
| Conta de serviço | **Obrigatória** sob `--vhost` (`--user`); opcional caso contrário | Compartilhável apenas fora de um virtualhost |
| Pacotes, Java, Node, servidor PostgreSQL | — | Já instalados |
