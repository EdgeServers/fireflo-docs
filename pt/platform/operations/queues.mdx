title: "Inspecionando uma fila"
description: "Profundidade te diz que algo está travado; um dump te diz o quê. O único campo que separa um problema de volume de um problema de fornecedor — e como limpar uma fila com honestidade quando as mensagens dela nunca serão enviadas."
---

`/ops/health` diz quão profunda é cada fila. Isso é suficiente para saber que algo está travado e
**não é suficiente para fazer algo a respeito**: 4 000 mensagens esperando em `vendor1` lê idêntico
seja um lote de um cliente que deu errado ou toda conta na máquina.

```bash
./scripts/fireflo queue dump
./scripts/fireflo queue dump vendor1
./scripts/fireflo queue dump vendor1 100
```

Um número solto é lido como um **limite**, não como nome de worker, então `queue dump 100` alarga
tudo. O padrão é 20 por fila, teto 500 — além disso a pergunta pertence a `cdr_submit` em vez de a
um gateway ao vivo.

```json
{
  "data": {
    "observed_at": "2026-08-09T02:14:07Z",
    "limit_per_queue": 20,
    "queues": [
      {
        "name": "router", "kind": "router", "depth": 1204, "ordered": true, "returned": 20,
        "entries": [
          {
            "serial": "01JC8…", "account": "acct-in-2001", "product": "in-otp",
            "from": "SUNOTP", "to": "919876543210",
            "body_chars": 44, "encoding": "gsm7", "parts": 1,
            "retries": 0, "priority": 2, "ingress": "http", "target": "in-sim",
            "queued_at": "2026-08-09T02:14:05Z"
          }
        ]
      }
    ]
  }
}
```

## Os quatro tipos

| `kind` | Contém |
| :--- | :--- |
| `router` | Aceito, ainda não roteado. **Uma fila para o gateway inteiro.** |
| `pending` | Roteado a um fornecedor, esperando a sessão dele. Uma por worker. |
| `delayed` | Retries agendados. `ready_in_ms` diz quanto até cada um estar elegível. |
| `broker` | Retido no RabbitMQ. **Apenas profundidade** — veja abaixo. |

## `retries` é o campo que responde a pergunta

<Tip>
**Uma fila cheia de zeros é um problema de volume** — chegaram mais do que o fornecedor aguenta.

**Uma fila cheia de retries não-zero é um problema de fornecedor** — as mesmas mensagens continuam
voltando.

Essas pedem respostas opostas. Adicionar capacidade a uma tempestade de retries piora; suspender um
fornecedor que está meramente ocupado move o backlog para algum lugar mais caro.
</Tip>

**`depth` e `returned` são perguntas diferentes.** `depth` é a fila inteira; `returned` é quanto foi
listado. Compará-los é como você sabe se está vendo o problema ou um canto dele.

## Sem texto de mensagem, e nenhuma flag que adiciona um

`cdr_submit` exclui o corpo por princípio — destino e origem são mantidos porque rating e disputas
precisam deles, o texto não porque operar um gateway nunca precisa.

Um dump de fila herda essa regra em vez de virar a única superfície de operador que devolve tráfego
de cliente em massa.

`body_chars` com `encoding` distingue um OTP de uma parte de um blast de seis partes travado, que é
a pergunta diagnóstica realmente sendo feita.

## Nada é consumido e nada é reordenado

Cada fila é percorrida com seu próprio iterador **enquanto o gateway continua drenando ela**. Então:

- Uma mensagem listada pode já ter ido embora quando você lê.
- `depth` é amostrado depois da caminhada e pode discordar de `entries` por alguns.
- `ordered` diz se a lista é a ordem em que o gateway vai enviar — **false** para uma priority
  queue e para a delay queue.

Essa é a troca honesta. A alternativa é parar o tráfego para poder olhá-lo.

## Uma fila de broker é reportada mas nunca percorrida

AMQP não tem jeito de olhar uma mensagem enfileirada sem tirá-la. `basicGet` mais um requeue
reordenaria a fila e resetaria contadores de entrega em mensagens de clientes pagantes para satisfazer
um diagnóstico.

Então a profundidade é reportada e o dump diz isso. **Um broker que não está respondendo reporta a
profundidade como unknown em vez de zero** — o que importa, porque zero é uma afirmação e unknown
não é.

## Limpando uma fila: arquivar e encerrar

<Warning>
**Stop sending ou Hold primeiro.** Se você precisa que o tráfego pare, suspenda o fornecedor ou segure
o listener ([Controlando um worker](/platform/operations/worker-control)) — nada se perde, e retomar
continua de onde parou. Limpe uma fila só para mensagens que nunca serão enviadas: um fornecedor que
deixou de existir, um estacionamento de roteamento que ninguém vai consertar, receipts para um login
que nunca mais vai fazer bind.
</Warning>

A partir da 0.12.19 uma fila pode ser limpa, pela linha de comando ou pelo painel de controle; os dois
chamam o mesmo endpoint do gateway, com o token admin:

```bash
./scripts/fireflo queue archive worker --worker smppclient.vendor1 --sub held   # dry run: counts, refund total, sample
FIREFLO_QUEUE_ARCHIVE=true ./scripts/fireflo queue archive worker --worker smppclient.vendor1 --sub held \
      --note "vendor withdrawn" --yes
```

O que acontece com cada mensagem que casa, nesta ordem:

1. **Tirada da fila** — de forma atômica: uma mensagem é pega pela sessão do fornecedor ou pela
   limpeza, nunca pelas duas. O gateway continua rodando; nada precisa ser suspenso antes.
2. **Arquivada**, em uma única transação confirmada no banco, com quem fez, por quê (a nota) e o lote
   a que pertence. Se o arquivo não puder ser escrito, todas as mensagens voltam para a fila e o
   comando responde que não conseguiu — nada se perde.
3. **Encerrada**, exatamente como uma mensagem que o próprio gateway descarta: **reembolsada** se foi
   cobrada, um **receipt de falha** enviado onde o cliente pediu um, e registrada como `REJECTED` com
   motivo `operatorPurge` — que é o que a timeline da mensagem e a página Refused mostram.

Receipts esperando por um login e retentativas de callback de webhook não carregam dinheiro: são
arquivados e removidos. **Nada arquivado pode ser devolvido** — limpar encerra uma mensagem, não a
estaciona.

| Store | Contém | Sub-stores |
| :--- | :--- | :--- |
| `worker` | As filas de um fornecedor ou de um listener | `pending`, `retry`, `held` (enquanto parado), `parked` (a entrada de um listener enquanto parado) |
| `routing` | As filas do gateway inteiro antes de um fornecedor ser escolhido | `router`, `retry`, `failed` (estacionamento de roteamento com falha) |
| `receipts` | Receipts esperando que um login SMPP faça bind | por login ou conta |
| `callbacks` | Callbacks de webhook esperando retentativa | por conta |

Uma limpeza de um store `worker` ou `routing` sem fornecedor, listener, conta ou login indicado é
recusada, a menos que você diga `--all`. Cada chamada arquiva no máximo 10 000; o comando e o painel
trabalham em lotes até nada mais casar.

<Note>
**Uma fila mantida no message broker não pode ser limpa.** O AMQP não consegue ler uma mensagem sem
tirá-la, e uma limpeza precisa ver uma mensagem para arquivá-la — então uma fila no broker é recusada
com `broker-backed`, e as ferramentas do próprio broker são o caminho para lidar com ela.
</Note>

O arquivo é lido em **Reports → Archives → Queue housekeeping** no painel, ou com
`fireflo queue archived` e `fireflo queue archive summary`; ele é mantido em partições mensais ao lado
de um resumo por dia que nunca é apagado. Veja [a referência de comandos](/reference/cli/fireflo#queues).

## Acesso

O token de **leitura**, não o admin. Um dump não tira e não move nada, então um sistema de
monitoramento que segura o segredo de observação pode pedir.
